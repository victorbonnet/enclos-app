# enclos app: what it does

The enclos app is a channel to the agents of a person's enclos hosts: from a phone, over their tailnet, they list each host's sandboxes and agents, talk to any of them, and read what an agent sends on its own, such as a cron job's output. enclos's side is in its design: [ADR 0042](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0042-a-bridge-on-each-host-serves-the-mobile-app.md) (a bridge on each host), [ADR 0043](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0043-sharing-an-agent-is-not-hosting-it.md) (sharing) and `docs/protocol.md` (the device leg), all proposed. The plan is in [enclos#145](https://github.com/victorbonnet/enclos/issues/145).

This file says how the app behaves, on every platform. Android is built; iOS is not started. **Both platforms behave the same and each looks native**: a behaviour here holds on both, and the [Platforms](#platforms) table says how each renders it. A pull request that changes a behaviour changes this file; a decision that is hard to reverse gets an ADR in `docs/adr/`.

Three kinds of statement are kept apart, as in enclos: what is decided (this text, an accepted ADR), what is proposed (an ADR with `status: proposed`), and what is still [to verify](#to-verify). Nothing here describes security behaviour as tested unless a test or a probe shows it.

Words are enclos's ([GLOSSARY.md](https://github.com/victorbonnet/enclos/blob/main/GLOSSARY.md)): host, sandbox, agent, runtime, channel, and for the app, bridge, person, paired device, conversation.

## 1. Shape

- **One Rust core, a native app per platform** ([ADR 0001](adr/0001-one-rust-core-and-a-native-app-per-platform.md)). The core (`core-ffi/`, over enclos's `enclos-protocol`) does the protocol's cryptography: pairing links, the Noise handshake, sealing and opening messages, and push previews. Each app does everything else natively: screens, the connection, storage, keys.
- **Hosts are independent.** The app pairs with each host's bridge on its own and gathers their agents into one list. No host knows of another.

## 2. Pairing

1. On the host, `enclos app pair` shows a QR code and a link (`enclos://pair?…`) that works once, for 5 minutes, while `enclos app serve` runs.
2. The person scans the code, types or pastes a link, or taps it wherever it is: the app opens on any `enclos://pair` link. A chat or a note opens only https links, so `enclos app pair` also prints `https://<bridge>/pair#…`, a page of the bridge whose "Open in enclos" opens the `enclos://pair` link (enclos `docs/protocol.md`, Pairing); pasted in the app, that https link reads as the other, but only when its own address is the bridge address it carries (as the bridge prints it): one that names another address is refused, since the person checks the address at the start of the link. The app reads the host's name, its bridge's address and the link's expiry, and shows them with a countdown. The address is the bridge's host name and port only: a link whose `url` holds a path, a query or no host name is refused, so what is shown is where the app connects. A link that is not a pairing link is refused with the app's own reason, never the link's text. A tapped link pairs only once the person confirms ("Pair with <host>?", Pair or Not now), since any page or message can hold one; a link opened while a pairing goes on is ignored, and so is one opened before (the system hands it again when it restarts the app, after an update): such a link can still be typed.
3. The app makes the device's signing key in the platform's key store (StrongBox where the phone has it) and a Noise key pair, wrapped by the key store.
4. It connects, sends a pairing request (its model name, its public key, a proof from the link's code), and shows the terminal's question: `<model> (tailscale login: <your login>) wants to pair. Accept? [y/N]`. The person answers in the terminal; the app shows Paired or why not (refused, or the connection ended). A pairing that ends unpaired deletes the signing key made for it.

The pairing screen has three steps, always in this order: code read, device key made, accept on the host. Its copy states what happens, never how safe it is.

**A link naming a host already paired.** A pairing link gives the host's name itself, so a name proves nothing; the bridge's key, which the Noise handshake checks, tells one bridge from another. When the link names a host this phone is already paired with:

- **Same bridge key**: the app pairs again, as for a new host. Once the bridge accepts, the new pairing takes the old one's place and the old pairing's device key is deleted from the key store; what the host sent before is forgotten, as for any pairing again ([On the phone](#8-on-the-phone)).
- **Another bridge key**: the app makes no key and does not connect. It shows a card, "Replace <host>?", with the paired bridge's address and the link's. **Keep <host>** leaves the pairing as it was. **Replace** pairs with the link's bridge; once it accepts, the old pairing, its device key and what the app showed of that host are gone.

The replaced host still lists this phone as a paired device until it is removed on that host.

**A pairing that is not accepted** (refused, the link expired, the connection ended, the key could not be made) deletes the device key it made. The keys are made off the main thread, and a failure to make them ends the pairing with its reason.

## 3. Connection

- The app opens a connection to each paired host when it comes to the foreground, and keeps it while the phone lets it.
- A connection that ends while the app is in the foreground is opened again after 2 s, then 4, 8, 16, 32, then every 60 s, until it is authenticated. Reconnect in Settings tries at once.
- On each connection the app asks for the host's agents and syncs the messages after the newest one it [keeps](#8-on-the-phone) from that host (every message, the first time); the bridge sends each message with the time it was stored.
- In the background the app does not connect. Until push notifications are built, what arrives meanwhile is shown at the next sync.
- When the bridge reports an error (an agent it could not reach), the conversation and Settings show it, in the bridge's words.

A message from the bridge that the app cannot read (a field missing, as from another version of `enclos app serve`) ends that host's connection, with that reason on screen. The app does not open it again on its own, since the next connection would get the same message: Reconnect does, or the app's next return to the foreground.

## 4. Screens

**The first screen** has two views, the conversations (the [inbox](#inbox)) and the [agents](#agents). Its top line holds the switch between them (a pill with the conversations' bubble and the agents' glyph, the one shown on `surface`), then, on the conversations, unread only, and Settings' gear. Swiping left on the main content opens the agents; swiping right returns to the conversations. The content follows the finger and settles on a view when released; there is no wrapping at either end. The switch shows the view a swipe would settle on and can still be tapped; the actions on the top line and the search field's label change once the swipe has settled. Vertical swipes scroll the current list. Over the end of the view, on a fade to the ground, sit the search for that view (a pill on `surface`: "Search conversations", "Search agents") and the compose button, which opens a [new conversation](#new-conversation); both show once a host is paired, and stay in place while the views slide, with the same search text across both. Back from the agents view leads to the conversations. Pairing a host lands on the agents.

**Full screens** arrive over it from the right: a conversation, an [agent's page](#an-agents-page), a [sandbox's page](#agents), a new conversation, [Settings](#settings), pairing and a policy request. Back from each leads to the first screen, except an agent's page opened from its sandbox's page, which goes back to that page. The app is in portrait only, for now, the QR scanner included.

### Inbox

By agent, within the selected active or archived view: one row per agent with a matching conversation, the agent with the newest matching conversation first. In the active view, only its conversations with something unread show under it while folded, so a new message is one tap away without the list growing with every conversation. The archived view shows all matching conversations expanded.

**An agent's row** shows its avatar (its initial inside the logo's corners, in `accent` while its host is connected, pulsing while it works), its name, the time of its newest message in any conversation (today: `07:12`, this week: the weekday, else `3 Nov`), and its [Home](#home)'s last message (words without markdown on two lines at most, the person's own prefixed "You:") with Home's unread count. While the agent works, the wave and what it does take the message's place, with where when that is not Home (`· in Weather in Lyon`, `· in 2 conversations`). Tapping the row opens Home.

**What is folded** is said at the end of the agent's group, on a line of its own starting where its conversations do, in `accent`, with a chevron pointing down: `17 conversations`, or `15 more conversations` when some show already. Tapping it unfolds them all, newest first, and the line, now at the end of the list, says `Show less` with the chevron pointing up. An agent stays unfolded while the app runs; with nothing folded away, there is no line.

**A long press on an agent's row** (with a haptic tick) opens its menu under its name: **New conversation** with it (not while its host no longer lists it), **All conversations** or **Fewer conversations** (as the line above, when some are folded away), **Routines** when its runtime supports them, and, under a line, **About** the agent, its page.

**Sections fold.** The Groups and Agents headings each fold their section away, or back, when tapped: the name, small and faint with no line under it, and a chevron at its end, pointing down while open and right while folded, turning between the two. A folded section shows its unread count by its name. What is folded stays so across starts of the app; a search shows all it finds, with the headings unfoldable meanwhile.

**A conversation under its agent** starts where the agent's name does, without an avatar: its [name](#names) ("No name yet" while it has none), the time of its last message, an "on its own" header when the agent sent it unprompted, the last message's words (or, while the agent works on it, the wave and what it does), and the unread count. A conversation with no message is not listed (one left empty, here or on an earlier version of the app). With no conversation yet, it points to the compose button. With no host paired, the inbox says how to pair one.

**Search.** The search at the bottom finds conversations by their name, their agent's address, and what was said in them (the agent's messages as their words, without markdown), whatever the case and the accents; with several words, each must be found, in the name or in any of its messages, not necessarily the same one. A conversation found by a message shows that message, the newest that holds the most words, in place of the last, with the words in `accent` (Home's, on its agent's row). Search reads every message, so it runs off the main thread, each message's words worked out once while the app runs. While searching or showing unread only, only agents with something found show, and everything found shows under them, folded or not, with nothing to unfold. Nothing found says so.

**Filters.** One Filters button on the title's line opens a menu with two independent toggles: **Unread only** and **Archived conversations**. It appears in Inbox when a host is paired. Both start off, showing all active conversations. Unread only limits the selected active or archived view to conversations with something unread; selecting both shows unread archived conversations. Changes apply immediately, and the menu stays open while toggling so both options can be adjusted together. The selections stay when switching between Inbox and Agents. With either toggle on, the button uses `accent` and a subtle accent surface, and its accessible state names each filter that is on ("Unread only", "Archived conversations", or both); with both off, it uses `text-muted` and its state says no filters are active. There is no filter by agent, since the inbox is by agent already.

### Archived conversations

The Inbox starts with active conversations. Turning on **Archived conversations** in Filters selects the archived view; turning it off returns to active conversations. Search and unread-only filtering remain available within the selected view. Policy requests appear only in the active view; groups remain their own section in both views. An archived conversation keeps its identity and every message, file description, name, read position and group member. The Archived view can find it by the same names, addresses and message text as the active view; **Unarchive** restores that same conversation and history ([ADR 0006](adr/0006-archived-conversations-are-a-restorable-inbox-view.md), proposed).

**Archive** is available from a direct or group conversation's actions and its long-press menu. Home cannot be archived and offers no **Archive** action; an ordinary conversation named Home can still be archived. Archived conversations, including a Home archived by an older version, offer **Unarchive** instead. Both actions require the host to be connected; while offline the disabled control says `Connect to <host> to change archive state.` While waiting it says **Saving archive state…**; with no answer from the host within a minute, it stops waiting and says to reconnect and check the archive state before trying again. Nothing is queued offline or hidden optimistically: the list changes when the bridge sends the new metadata. The bridge owns this state and sends it to the person's other paired devices and at every sync, so reconnecting, clearing the phone cache or pairing another phone restores the same archived state.

Conversation metadata carries the bridge's revision; the phone keeps the highest it saw for each conversation and ignores a lower one, so a delayed broadcast cannot undo a newer archive, name or read state. Revisions assume a bridge's database is never reset or restored from an older copy: after that, a reused id (a Home's) keeps its older state on the phone until the person clears the cache. The phone keys conversations by id. A Home's id, `home.<sandbox>.<agent>`, is the same on two hosts that both have that sandbox and agent: the phone keeps the first host's and leaves the second's out, with its messages, typing, tool steps and group state, rather than mixing them or letting one replace the other. The second host's heading in Agents says how many of its conversations are not shown and why, and that agent's page says its Home is not shown here. Showing both needs the cache keyed by host as well (see [To verify](#to-verify)).

Archived conversations contribute no preview, newest-message ordering or unread count to the active Inbox and its folded-section counts. An agent with no conversation in the selected view is absent. Its header opens Home only when Home belongs to that view; otherwise it is a heading for its matching conversations, with no Home preview or tap target. Their stored read positions remain intact; opening one marks it read by the ordinary rule below. A new reply, status line or cron output stays in that archived conversation and leaves it archived. Direct and group conversations use the same actions. Archiving leaves running work and group discussions alone, and agents stay available in Agents. It calls no runtime archive command, resets no context and removes no saved memory: Hermes and a future OpenClaw channel share this app behaviour through enclos's conversation protocol.

### Home

Each agent has one Home conversation, which its host's bridge makes and keeps (enclos ADR 0044, `docs/protocol.md`, Home): the runtime's home channel. What belongs to no conversation lands there: a cron job that has no conversation of its own, a message the agent sends with no other place to go, the runtime's notices about itself. It is named Home, opened by its agent's row in the inbox, shown even when empty ("Cron jobs and the agent's notices come here."), and the person may talk to the agent in it too. A cron job started in a conversation still answers in that conversation. Hermes's `/sethome` is answered by its plugin, not run: there is nothing to set.

Home stays active and cannot be archived. A Home archived by an older version keeps the same id, history and delivery route and continues receiving output. It remains available in Archived conversations and from Agents; **Unarchive** restores it to the active Inbox. Opening it still marks its messages read normally; only Unarchive changes that legacy archived state.

**Status lines.** The runtime's notices about itself (Hermes: the gateway online, shutting down, restarting) are not the agent speaking: they come as `status` and show as a quiet centred line, small and faint, with their time, never a bubble. They never count as unread, and the inbox previews the last other message when there is one. The plugin, in the sandbox, chooses a message's kind, so a status line is the sandbox's word, never the app's or the bridge's: it starts with the runtime's name (`hermes: gateway online · 14:02`), is cut to one line, and drops the characters that would reorder or hide part of it. One that carries files shows as a message, so its files show. Status lines coming only from the runtime's gateway, never from a turn, would have to be enforced on the bridge; the app does not.

### Sandbox policy requests

**Above Groups in the inbox**, a Sandbox requests section shows pending, applying and failed policy requests from all paired hosts, newest first, even when there is no conversation. Its heading folds the section away and back, with the same chevron as Groups and Agents and the request count beside it while folded. The folded state stays across starts; a search temporarily unfolds matching requests and disables folding, as for the other sections. Search matches their target, sandbox and host; the unread-only filter does not hide them. Each request is a compact two-line list row, without a card or inline decision controls: the action on one line (a file target uses its final name, such as `Write to enclos`), then its agent when known, sandbox and host on one metadata line. The requesting agent's usual round, coloured avatar leads the row at 32 dp, matching that same agent elsewhere, and their name appears first in its metadata. A proxy-only refusal has no known agent: it uses the Enclos mark in grey (the theme's faint text colour, so it follows dark mode), in the same 32 dp space and says `Agent unknown`, without attributing it to an agent. Both lines truncate with an ellipsis. Saving, failed and unavailable requests add a short status to the metadata. The whole row opens its detail page. Its spacing, sans-serif metadata, title-line chevron and absence of dividers match the inbox's agent rows. A proxy refusal names the sandbox, since its host cannot identify an agent. The full target, policy scope, reasons and **Approve** / **Deny** controls appear only on the detail page.

Tapping the row opens its detail page: attempted action, the selectable scope approval writes, who requested it, the exact change the host described, private-address access if requested, and whether all running sandbox work ends for a restart. It links to the originating conversation when one is known, and shows the decision controls at the bottom. A file change requiring a restart says **Approve & restart**; unsupported scopes explain why and keep approval disabled. It says approval persists for every agent of that sandbox and updates their policy knowledge for later work. An approval does not automatically retry the attempted action. Network scopes are one host:port; write scopes cover the named path and everything beneath it. The row title and the detail page lead with the host's `scope`, the normalized destination or the writable path with its symlinks resolved, never with the agent's own text over it; when the host resolved a write path through a link to another place, the page also shows the requested path and says approval grants the folder it leads to, not the link. A host that sends no `scope` (before enclos's change) shows the requested target. The agent's action label is shown without hidden characters, and a target's hidden characters are written out (⟨U+202E⟩), never applied. A request the bridge sends without a field the app needs (its id, sandbox, state, time or access) is dropped, never shown and never fatal. Sensitive read denials remain unavailable for approval. Host behaviour is [enclos ADR 0046](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0046-the-hosts-person-approves-sandbox-policy-scopes-from-the-phone.md), proposed; this is a sandbox policy request, not a runtime tool approval.

Only the host's own person on a still-paired device may decide. Approve and Deny each ask for the phone's biometric or screen lock first (the [app lock](#app-lock)'s prompt: a strong biometric or the screen lock), every time and whatever the app-lock setting, so a phone left unlocked in someone else's hands cannot widen an agent's access; cancelled or failed, nothing is sent and the page says what the system said. A phone without a screen lock cannot decide, and the page says to set one. Buttons need a connected host and a completed fresh sync, remain disabled during a decision, and show Saving decision. Nothing is queued offline or optimistically marked approved. A changed policy refreshes the preview; the person must review it again. A request decided on another device shows that result. Completed approvals and denials leave the inbox but stay on an open detail page; failed or interrupted applications stay visible with a reason to review the host's policy. They are not retried automatically.

Requests are kept in the app's private preferences, covered by its existing no-backup rules. On authentication the host's cached requests are replaced by its fresh sync; forgetting that host or clearing the cache removes them. They show offline with both controls disabled. Android is built; iOS follows the same behaviour when implemented.

Connections attributed to a host policy-test run stay blocked and logged but never become inbox requests, including private-IP probes. The proxy verifies a host-registered, sandbox-scoped marker; arbitrary client markers cannot hide normal traffic. A genuine agent request to the same address remains visible. The built-in network probe's reserved `probe.enclos.invalid` destination is not an approval request. The host suppresses new notifications for that exact host and retires existing pending ones as diagnostics without changing policy. Such notifications leave the inbox; a detail page already open says **Diagnostic probe · no approval needed** and offers no decision controls. Real destinations, including private addresses, remain eligible for requests.

### Groups

A group is one conversation between the person and two to six agents of **one sandbox**, which the host's bridge keeps and whose turns it runs (enclos ADR 0045, proposed; `docs/protocol.md`, Groups): the app shows it and sends the person's messages.

- **Starting one**: the compose button's agent chip lists **New group** when a sandbox has at least two agents. Its agents are ticked (once one is, only the agents of its sandbox can be), with a name or none (their names then); the first message starts the group (`group.new`, then the message). A group the bridge refuses (an `error` naming the `group.new`: a member it no longer knows, an older bridge) leaves the phone at once, and where it was started, or opened, says `The group was not started:` and the bridge's words.
- **In the conversations view**: a **Groups** section above the agents, each group with its members' avatars overlapping, its name, its last message with who said it, how long ago or the working wave, and its unread count. Groups are not in an agent's tree.
- **In the group**: the members' avatars and handles in the bar; each agent message with its speaker's avatar and name above it. Typing `@` lists the members matching what follows, with their avatars, and **@all** last ("everyone answers"); picking one puts `@handle ` in the field. `@handle` addresses that member, several those members, `@all` every member, each of whom must answer; a message naming no one invites them all, and they may pass.
- **Where it is**: a line over the field, from the bridge's `group.state`: `@coder is answering · round 1 of 3` with the wave and **Stop** (`group.stop`, which cancels what is queued and the running turn; what was said stays), then Settled, Paused after the rounds or the replies allowed, Stopped, or Failed with why.

### Names

A conversation has a name: its agent's, from what was said in it (Hermes names each session; the plugin passes the model's summary on, not the first message's cut), or the person's. Tapping the name in a conversation's bar renames it; the person's name replaces the agent's, which no longer replaces it, and clearing it lets the agent name it again. The bridge keeps the name and sends it to every device of the person (enclos `docs/protocol.md`, A conversation's name), so a name is saved only while its host is connected: until then the rename dialog says so and cannot save. A name is shown without the characters that change how text reads unseen (bidirectional overrides, zero-width characters: the app's `Visible` rule), whoever gave it.

### Agents

**By host, then sandbox.** Each paired host has a heading, even when it is the only one: its connection (a filled square in `accent` while connected, an outlined one otherwise) and its name, with the chevron of the conversations view's sections, folding the host's sandboxes and agents away or back; what is folded stays so across starts, and a search shows only the hosts with something found, unfolded. A host with no agent yet says the host lists them once connected. Under it, each sandbox's heading (the Enclos mark, its name, its runtime), then its agents. No heading has a line under it.

**A sandbox's page.** Each sandbox heading in the agents view ends with a chevron, and tapping it opens the sandbox's page: its mark (in `accent` while its host is connected), its name, runtime and host; its agents as the agents view shows them, each opening its page (back from which returns to the sandbox's page); its groups, each opening; what it runs on (runtime, host and connection); a Policy row with accepted-access count and active version, opening the policy page below; and a line saying its remaining state and sessions show on the host (`enclos sandbox show <sandbox>`).

**An agent's row**: its avatar (pulsing while it works), its name, and, while it works, the wave and what it does (the tool it runs, as its label says, else `working`), else when it last sent a message (`active 3 hours ago`, `active yesterday`, its runtime's notices aside), `no message yet` before its first one; a chevron at its end, and tapping it opens [its page](#an-agents-page). An agent works on a conversation from the person's message until its answer, while its runtime says it is writing, and while a tool it started has not ended; the phone knows only what comes over the bridge, so not, for instance, a cron job the runtime runs without saying so.

The search finds agents by their address and runtime. With no host paired, the view says how to pair one. A person sees only what is shared with them; the list never hints that more exists.

### An agent's page

Opened from an agent's row, its menu's About, or a sandbox's page. Its avatar (pulsing while it works), name and address; **Conversations**: its [Home](#home) ("Cron jobs and the agent's notices come here."), which opens, **New conversation** with it, and how many other conversations it has, in the conversations view; **Runs on**: its runtime, sandbox, host and the host's connection, and what its channel lets it do once the bridge has reached its plugin (says when it is working, shows the tools it runs, names conversations, lists its commands, sends files), else that this is known once its host reaches it; **Commands**, when its runtime lists them, the first six with **Show all**. Read only: changing an agent from the app comes later, for the host's own user, which the page says.

### New conversation

The compose button's screen: Close; the agent it is with, a chip at the top (its avatar and name, the agent most recently active first), whose list picks another agent or starts a [group](#groups); the agent's card in the middle (avatar, name, sandbox, runtime and host, and how many commands it has); and the field. The first message starts the conversation (a draft until then, which the bridge learns of with that message, `conversation.new` then the message, so a screen left before sending leaves nothing behind) and opens it. A send that does not go leaves the person on the screen with the text, and the next tap reuses what the last one made: the same draft while the agent is the same (another agent's draft is dropped), the same group while its members and name are the same, so a failed send makes no second group on the host. Sending needs the agent's host connected, as in a conversation. A conversation screen whose conversation the phone does not hold (a draft lost when the system stopped the app, or one forgotten or cleared while open) goes back to the first screen.

### Routines

The list and editor use the same visual controls as the rest of the app: hairline-separated rows, outlined schedule choices, 12 dp form controls, the shared primary button and the app-lock switch colours. Addresses and run metadata use the existing monospace styles; confirmations reuse the app's shared dialog. Light and dark themes use only the app palette, including selected and disabled controls.

An agent advertising `routines` offers **Routines** from its actions and agent page to the person its host lets manage them (`can_manage_routines` in the agent list: the host's person only, and no one on an older host that does not say); a person the agent is only shared with sees no Routines entry. The page is scoped to that agent on its host, with a back action, add action, refresh and a **Nothing scheduled** empty state. It lists enabled, paused and completed routines with schedule, next run and last observed result; selecting one loads the current editable definition. The runtime owns definitions and execution ([ADR 0007](adr/0007-routines-are-runtime-owned-controls.md), proposed), so the app must refresh to see changes made by its own tools or another device. Lists are paged and never download every routine's full prompt at once.

The create/edit flow has an optional name, instructions, schedule and **Send to**. Daily starts at 09:00; Weekly chooses weekdays and a time; Monthly chooses a day and time; Repeat chooses a positive interval; Once chooses a date and time; Custom accepts a cron expression. The editor preserves a custom expression when it cannot be represented by a preset. Scheduling uses the runtime's reported timezone, shown in the editor, including when it differs from the phone. Next/last-run times are observed runtime values, not local predictions. **Nowhere** saves the result only; authorized direct conversations and Home with this agent can receive it, including archived direct conversations and a Home archived by an older version. Routines with existing external destinations, a secondary failure destination, a custom endpoint, monitors, chained context or session attachment are shown read-only, preserving their native settings.

Advanced settings are offered only when supported: skills loaded before the instructions, a model/provider override or runtime default, default toolsets versus an explicit selection, script-only execution, a relative script path and an absolute working directory. Catalog suggestions keep model/provider pairs together; explicit model, skill and toolset IDs allow values outside the bounded suggestion list. A refreshed runtime timezone differing from the editor’s initial zone requires reopening before saving. Default toolsets and an empty selection are distinct. Script-only requires a script and delivers its output without a model; a script is a file in the agent's scripts directory, never a command line. Working directory and script settings grant no additional sandbox access. Unknown existing native settings survive edits.

The page supports editing, explicit pause/resume, running now (an enabled routine only: a paused one is resumed first; confirmed first, naming the routine and where its output goes) and confirmed deletion. Deletion removes the runtime definition and may remove its saved output; it does not promise to stop an already-running execution. Controls wait for correlated replies and show failures beside the affected flow. Definition revisions prevent an old editor replacing another edit; a conflict requires reloading. Offline controls are disabled with a connection explanation. A timeout or disconnect after dispatch can mean the outcome is unknown: refresh before deciding whether to try again. Mutations are neither queued offline nor automatically resent. Management initially requires the host's person; the bridge enforces this and validates delivery choices, independently of the app. A routine that changed since the person chose it (a refresh brought a new revision) is not acted on, and the page says so.

What the runtime writes is shown as its text, never as the app's: names, previews, delivery and choice labels, states, pause reasons, last results and errors and the time zone are drawn without the control, bidirectional and invisible characters that would change how they read (the same rule as enclos-protocol's `visible` module; joiners between non-ASCII characters are text), and a refusal from the host is quoted as the host's reply. The definition, which goes back to the runtime, is kept as it came: when its name or instructions hold such characters, the editor says so and saves them unchanged.

### Agent display names

The agent page offers **Rename** for its shared display name, using the same field and actions as the app's other editors. The host stores this name and supplies it to every connected app that can see the agent ([enclos ADR 0051](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0051-agent-display-names-belong-to-the-bridge.md), proposed). This is shared agent presentation metadata, rather than a private phone preference. Only the host's person on a still-paired device may change it.

For example, `comptoir-dev` can appear as **Gégé Commit**. Display names support Unicode and spaces, are trimmed, and must contain 1–100 Unicode code points using at most 400 UTF-8 bytes, without controls, line separators or characters that change how text reads without showing (bidirectional overrides and isolates, zero-width and other default-ignorable characters, the soft hyphen, tag characters, variation selectors and blank fillers: the same rule as enclos-protocol's `visible` module), so a name cannot read as another agent's. The zero-width joiner and non-joiner and the emoji variation selectors are part of a name only between two non-ASCII characters, as in a joined emoji or Persian spelling; next to ASCII, at an end or beside another such character they are refused. The editor refuses such a name; a listed name holding one is not shown, and the handle stands in for it. The host also refuses a name that reads as another listed agent's handle. Two names that differ only by joiners read alike: a mention suggestion shows a display name beside its `@handle` only when it reads differently. **Use original name** explicitly clears the display name. The stable address stays visible on the agent page; addresses, conversation identity, runtime configuration and `@handles` do not change. The agent's own memory, prompt and native channel name stay as they were.

Lists, agent pages, unnamed conversation headers, group member/speaker labels, avatar initials and accessibility labels use the current shared display name, falling back to the stable handle when no name is set. Older messages' agent labels resolve the same current name; message records and conversation titles are not rewritten. Search finds both display name and stable address/handle. Mention suggestions show the display name with the handle and still insert the stable `@handle`. Duplicate display names are allowed, so addresses/handles remain available to distinguish agents.

The editor fetches current metadata before editing, retains its opening revision and waits for a correlated host confirmation. Nothing is renamed optimistically or queued offline. A stale edit requires reloading/reopening; the new host metadata does not silently replace a draft or count as its successful save. Disconnect or a missing confirmation requires refreshing before retrying. The phone keeps the highest name revision it saw for each agent address; after a bridge's database is reset or restored from an older copy, it keeps its older name until the person clears the cache. Offline, non-owner and unsupported-host states explain why editing is unavailable; an older host says to update the host. This change does not deploy or restart a bridge.

Android caches the display name and its nonnegative revision in the agent row, scoped by host and canonical agent identifier. The additive cache upgrade retains existing agents and conversations, with revision 0 and no display name for older rows. Lists, broadcasts and background cache reads preserve the newest observed name revision. Clear cache and Forget this host remove only the phone's copy, and reconnect restores the host's value. Android implements this first; iOS follows the same behaviour when built.

### Agent photos

Tapping the avatar on the agent page opens the photo picker. When a photo is set, **Remove photo** appears below it. There is no separate Change photo button. A photo belongs to the agent on its host and is shared across apps connected to that host. The host owner can edit it while connected to a supporting host; other paired people can see it. The platform's photo picker grants access only to the selected photo. Cancel leaves it unchanged. The app prepares a small square photo, then waits for host confirmation; progress and failures appear by the controls. Remove asks for confirmation and restores the coloured initial everywhere. An older host keeps the initial and disables changing the photo.

The same round photo appears in agent and inbox rows, agent pages, conversation headers, group stacks and speakers, mentions and identified sandbox requests. Working indicators remain visible. With no custom photo, existing initials remain; with one or without, the agent row's corners still say whether its host is connected. Photos are keyed by the host and the agent kept apart (never one joined string, since a host's name may hold `/`), so equal agent names on different sandboxes or hosts do not share an image. The app takes a photo only for an agent its host lists, drops it when the host no longer lists the agent, and keeps at most 64 photos per host. The host's agent list is its word on each photo, even at a lower revision than the phone last saw (the host's database may have been made again); between lists, older revisions are ignored. When the host confirms a photo this phone just set but the phone does not take it (past its 64, or the agent no longer listed), the photo controls say why instead of going quiet. A photo message without its agent or revision is ignored.

The host stores and versions the asset ([enclos protocol](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#shared-agent-photos)). Connected apps receive changes and removals, and reconnect fetches the current version. A stale edit is refused and refreshed so it cannot overwrite another device's change. Cached photos survive app starts for offline display, with editing disabled offline. Clear cache and Forget this host remove only the phone's copies; the shared host photo remains. Android is built; iOS follows when implemented.

### Sandbox policy management

The sandbox page's **Policy** row opens its active policy. Entries are grouped into collapsible sections for allowed destinations, private network access, writable paths, protected read paths, network mode and incoming connections, resource limits, network logging and secret references. Active entries that came from approvals say **Accepted access**; inherited and sandbox-specific settings name their origin. The active policy is the source, so removed entries stop appearing even though an approval remains in history. All accepted entries remain discoverable regardless of the inbox history window.

The host's person can add, edit or remove an access entry and change default settings for **this sandbox only**. Tapping an editable entry opens a small editor; **Remove** requests a removal. Values and the host's change lines are shown with their hidden characters written out (⟨U+202E⟩), and a typed value holding one is refused before any preview, so the review reads as what the host saves. **Review change** asks the host for exact effects, followed by **Save policy** or **Save & restart**, which asks for the phone's biometric or screen lock first (the [app lock](#app-lock)'s prompt: a strong biometric or the screen lock), every time and whatever the app-lock setting; cancelled or failed, nothing is sent and the review says what the system said. A phone without a screen lock cannot save a policy edit, and the review says to set one. The review explains when all running work ends and services restart. No change is optimistic or queued offline. The host refuses stale previews, pending or unapplied changes, invalid paths or destinations and protected built-in read-deny edits. Removing the last private destination also removes its unused private-address opt-in; public network mode's continuing web access is disclosed. Every agent receives updated active-policy knowledge after a save. Secret references and network logging are read-only; secret contents are never sent.

Cached policy is kept in the app's private preferences, under its no-backup rules, in plain text like the cached requests: it holds host paths, destinations and secret reference names, never secret contents. It is visible offline and survives app starts, but editing waits for a fresh host response on the current connection: a connection that ends or is replaced makes it stale again. Refresh asks again; another device's save updates this page and dismisses an obsolete review. Connection loss or a missing confirmation requires refreshing before trying again. Clear cache and Forget this host remove cached policy. Only a still-paired device of the host owner may load or change it; when the host answers that this person is not its own (an agent shared with them), the sandbox page drops its Policy row ([enclos ADR 0047](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0047-the-hosts-person-manages-sandbox-policy-from-the-phone.md), proposed). Android is built; iOS follows when implemented.

### Settings

In sections, each named small, faint and in capitals above a hairline, its rows separated by hairlines. Nothing here acts on a sandbox.

- **Hosts**: each paired host, its connection (who it is connected as, or why not), the bridge's last error, its address, then Reconnect (when it is not connected) and Forget this host on one line; and a last row, Pair a host, with the QR glyph.
- **Security**: the [app lock](#app-lock), a switch beside what it does; the whole row toggles it.
- **Appearance**: the [theme](#7-theme).
- **On this phone**: what is kept (and, when it could not be read, such as after going back to an older build, that it could not), and Clear cache.
- **About**: the app's version and the core's.

- **Forget this host**, after a confirmation: connected, the app asks the bridge to unpair this phone (enclos `docs/protocol.md`, `device.forget`); not connected, the host keeps it listed until `enclos app unpair` there, which the confirmation says; when the connection ended between the confirmation and Forget, the app says so after it. Either way the phone deletes its device key and Noise key for that host, and everything it kept from it: agents, conversations, messages, files (those of messages not read from the phone's copy yet too), how far they were read, whether its heading in the agents view was folded. Pairing again with a host deletes the device key of the pairing it replaces, and at each start the app deletes any device key no paired host uses. The conversations stay on the host. Using it again means pairing again.
- **Clear cache**, after a confirmation: deletes the conversations, messages, agents and files kept on this phone, then syncs everything again from each connected host. Pairings stay, and how far each conversation was read comes back from the bridges.

### Conversation

The conversation's name in the bar (the agent's name while it has none), the agent and its address under it; tapping them renames it. Messages bottom-up, anchored at the newest: the screen follows what arrives unless the person scrolled up to read, and stays anchored when the keyboard opens. A day separator in lowercase (`today`, `yesterday`, `mon 3 nov`) starts each day. Each message has its time (`HH:mm`).

- The person's messages: right, on `button-bg`, shown exactly as typed.
- The agent's: left, on `surface` with a hairline, [markdown](#5-messages) drawn, selectable to copy. One the agent sent on its own (`kind: notify`, such as a cron job's) has an "on its own" header; the protocol does not say which job.
- **The agent at work**: three squares rising in turn, a 900 ms wave, from the moment the person's message is sent until the agent answers, and whenever the runtime says it is typing. It stops when the connection ends, when the bridge refuses the message (an `error` naming it, such as `agent_unavailable`), and after 10 minutes with no word from the agent.
- **What it does** (runtimes with the `tools` capability): above the working wave, "Working · n steps" and each tool the agent runs, one a line: its mark (a square pulsing in `accent` while it runs, a check once done, a cross if it failed or a policy refused it), its name in mono, what it does (`ls -la`, `weather Lyon`) and how long it took. When the answer arrives, its steps fold into one line above it ("3 steps", with a chevron), which opens them. When the turn ends with no answer (the runtime stops typing), a step still running is marked done and the steps are no longer shown; an answer that follows still takes them, and the person's next message starts a turn with none. A tool's name and what it does show a hidden character as `⟨U+XXXX⟩` (the app's `Visible` rule). Steps come live from the bridge, which does not keep them: the phone keeps them with the answer they led to, so they stay after the app restarts, on that phone only (another device, or this one after missing them, shows the answer without its steps).
- Under the messages, why the host is not connected, or what the bridge said, when there is something to say.
- **Sending needs the host connected.** While it is not, the field still takes text, the send button stays off, and a line above the field says so (`Not connected to mac: send once it's back.`); nothing is queued to go later. What was written stays, for each conversation, while the app runs (leaving and coming back keeps it); Forget this host and Clear cache drop it with the conversations. Sending takes it out of the field, but it is sent only once the bridge shows it back as stored: should the connection end, or the bridge refuse it (`error` naming it), first, the text comes back to the field, before anything written since, and the line above says `Not sent:` and why. If the bridge had it after all, the next sync shows it and takes it out of the field again, unless the person changed it. A conversation started on the phone stays a draft until the bridge sends it back, so its start goes again with the next try.
- **The agent's commands** (runtimes with the `commands` capability; enclos `docs/protocol.md`, An agent's commands): typing `/` opens, over the field, the commands the agent's runtime lists, in its order, on `surface`; each `/name` in mono, what follows it faint (`[name]`, `<prompt>`), and what it does on one line. Typing more keeps the commands whose name starts with it, then those that have it elsewhere, whatever the case, with the typed part in `accent`; about four and a half rows show, the rest scroll. Picking one puts `/name ` in the field, the cursor after it, and the list closes, as it does once a space follows the name. A command is sent like any message, and the runtime answers it; the app runs nothing. The bridge sends the list after the agents' and when the runtime lists it anew; it is kept while the host is connected, and dropped by Forget this host and Clear cache. Each name shows once.

Opening a conversation marks it read, as does a message arriving while it is open: unread counts are the agent's messages after the last one read. The bridge keeps how far each conversation was read and sends it with the conversation, at each sync and when it moves (enclos `docs/protocol.md`, How far a conversation was read): a message read on one device is not unread on another, nor after pairing again. The runtime cannot tell, as it does not see what the person reads. A conversation read further while offline tells the bridge at the next sync. A position past the conversation's newest message is taken once its messages came, and never past the newest of them, as the bridge itself never goes further.

## 5. Messages

**Bubble width.** Messages grow with their content up to 90% of the available conversation width, capped at 640 dp/pt on large screens. The conversation keeps its side padding, and every bubble leaves a visible gap on its opposite side. Short messages keep their natural width. Android is built; iOS follows the same limit when implemented.

An agent's message is markdown ([ADR 0002](adr/0002-messages-are-markdown-drawn-by-the-app.md)): CommonMark, with GitHub's tables, strikethrough and bare links. The app draws it itself:

| Markdown | Drawn as |
| --- | --- |
| `**bold**`, `*italic*`, `~~struck~~` | semibold, italic, a line through |
| `` `code` `` | mono, in `accent` |
| `# Heading` (1 to 6) | semibold, 19, 17, then 15 sp/pt |
| lists, ordered or not, nested | a mono marker in `text-faint`, then the item |
| `> quote` | a 2 dp `accent` bar, the text in `text-muted` |
| fenced or indented code | mono on `panel-deep`, scrolling sideways |
| table | columns as wide as their widest cell (up to 240), header bold, hairlines between rows, scrolling sideways; at most 12 columns and 50 rows, the header included, with a line above saying how much is shown when there are more |
| `---` | a hairline |
| a single newline | a line break (CommonMark would join the lines; chat is written line by line) |

Nothing in a message is fetched or run:

- an image (`![alt](url)`) shows as its alt text and `↗`, a link to it; the app never loads it;
- HTML shows as its literal text;
- tapping an `http` or `https` link opens the preferred browser's Custom Tab on Android when the link's text is the very address it sends (a bare link); a link whose text is a label, an image's alt text, or an address the network spells otherwise (a look-alike name in another script) first shows the same sheet as an artefact's link (below), for the same reason: its address can carry what the agent wrote, past the label, and leaves the phone outside the sandbox's network policy. `mailto` uses the system mail handler. Any other scheme, and an `http` or `https` link with no host or with user-info (`https://bank.example@evil.example` reads as the bank), is plain text. The browser handles the opened website with its normal state and capabilities. A system URL handler for links that may be opened from the web (`BROWSABLE`) is the fallback when Custom Tabs are unavailable; no handler or a refused launch produces a native notice. Nothing is prewarmed or prefetched.
- a link's text drops hidden characters (bidirectional overrides, zero-width characters: the app's `Visible` rule), so it cannot read as another address;
- a `mailto` link opens the mail app with the recipient, subject and body the agent wrote; the person still decides to send it.

The person's own messages are not markdown: they show as typed. Previews (inbox, and later notifications) are the words without the marks.

### Questions

A structured question appears inside its agent's message, using the app's existing choice, field and button styles. The person selects one option, or several when the question allows it, and explicitly taps **Submit**. Nothing is selected initially, including an option labelled Recommended. Labels wrap in full. **Other** opens a text field and replaces any listed selection; a question without choices offers the text field directly. **Skip** is a separate explicit action. Empty answers cannot be submitted. The card opens with the app's own line, "The agent asks · answering changes no access", above the agent's text, so a question cannot pass for a sandbox access request. Android is built; iOS follows the same behaviour with native controls when implemented.

The card applies enclos-protocol's question rules before showing or sending anything: at most 12 one-line labels, distinct once joiners are set aside, the encoded size limits, and no hidden character (a control character, a bidirectional mark, embedding, override or isolate, a zero-width or other default-ignorable character, a line or paragraph separator, a tag, a variation selector, a blank filler or a soft hyphen; newlines aside in the question and in a typed answer), so one label cannot read as another. The joiners U+200C and U+200D and the emoji variation selectors U+FE0E and U+FE0F are ordinary text between two non-ASCII characters (Persian spelling, a joined emoji) and hidden anywhere else. A question that breaks them stays readable text. A typed answer is sent with its line breaks as plain newlines; one with a tab or another hidden character is not sent, and the card says why. These rules are written twice, in enclos-protocol (Rust, which the bridge applies) and in the app (Kotlin, `Questions.kt` and `Visible.kt`), with the same test cases: `core-ffi` pins enclos-protocol at a commit of enclos's `main` that predates the question module, so the app cannot call it yet. When that pin moves past it, the app should call the crate's rules through the core instead, which iOS then shares too.

How long a question stays open is the runtime's to decide: enclos sets Hermes's `agent.clarify_timeout` to an hour for the app's agents, after which the card shows Expired. An agent that stays disconnected for two hours has its questions expired by the bridge.

Only a message linked to valid structured metadata becomes a question card. An ordinary list, or a linked message whose metadata is unavailable, keeps its readable text. The optional runtime-neutral contract and its ownership/lifecycle decision are in enclos's [Questions protocol](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#questions) and [ADR 0052](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0052-questions-keep-their-runtime-waiter-and-structured-app-controls.md), proposed. Hermes first implements it through `clarify`; the channel hint and registered `enclos:app-questions` skill teach the agent to put options in the tool's choices.

Submitting resolves that exact waiting question; it sends no chat message and starts no new turn. Controls are disabled while offline, awaiting a receipt or after the question is answered, skipped, expired or cancelled. The card shows the confirmed answer or terminal notice. Another device's answer updates it too. The bridge marks a settlement `confirmed` only when it is the answer a paired device submitted, matched by its request; an answer or a skip the agent's channel reports on its own (a reply typed in the composer, say) reads "Answered, as the agent reports" or "Skipped, as the agent reports". A question may be answered with no answer the contract can carry (the runtime took a reply with a hidden character, for one): the card then says it was answered and shows no choice or text. An unrelated metadata broadcast is not confirmation of this device's submission. A disconnect, a lost receipt, or the bridge's `unconfirmed` error (or an error code the app does not know) may leave the outcome uncertain: the card explains it and does not resend automatically. Its pending state is refreshed by the next sync: the one after a reconnect, or one the card's **Check again** asks for over the open connection. The sync sends every pending question again, so one it sends may be answered again; until it ends the card says it is checking. A refusal the bridge makes before writing the answer to the agent (`agent_unavailable`, `bad_message`, `conflict`, `not_found`, `unsupported`, `not_allowed`) is certain: the card shows why and may be answered again. A runtime restart cannot recreate its old waiting call.

Question definitions, states, revisions and message links are cached per host with conversation history. Older cache versions migrate without losing messages. The newest confirmed revision wins over delayed network events or background cache loads; clearing cache or forgetting a host clears its questions too, and a cached question whose conversation is no longer kept, or which no longer reads as valid, is dropped when the cache loads. An older bridge/runtime keeps native text fallback, and older apps can answer the readable question through the runtime's text interceptor (an option's number or text, or "skip"; another message cancels the question and reaches the agent as a message).

### Runtime approvals

A supporting runtime's approval appears inside its agent's bubble under the app's own heading, "The runtime asks to run a command", then the runtime's text as plain body, the complete native display command and its reason ([ADR 0009](adr/0009-runtime-approvals-use-native-buttons-with-explicit-consent-scopes.md), proposed). The command is selectable text in mono, wrapped so that none of it is out of sight, with every hidden character (a control other than a newline, a bidirectional mark, a zero-width or other default-ignorable character, a soft hyphen; the shared rule of enclos-protocol's `visible` module) written out as `⟨U+XXXX⟩` and a tab as `⟨tab⟩`: what is shown is what runs. A run of two or more blank lines is written as one line `⟨N blank lines⟩` and a run of eight or more spaces as `⟨N spaces⟩`, so a stretch of nothing cannot push part of the command out of sight. A command holding a character outside ASCII carries a notice that some such characters look like others. The runtime's text and the reason are shown the same way.

The conversation opens on its newest item, so a card taller than the screen shows its buttons first. A command of more than four lines, or more than 240 characters, says next to the buttons how many lines and characters it has and that it starts above. Until the start of the command has been on screen, only Deny is available, and the card says so. Neither is rendered as markdown or run by the app. Buttons use the app's existing styles and tokens. An ordinary message containing `/approve` remains a message; native controls require linked, matching typed approval metadata. Approval metadata never uses the ordinary question picker.

Show only the runtime's offered actions, in order: **Allow once**, **Allow for session**, **Always allow**, **Deny**. A direct tap explicitly submits that action; nothing is selected or submitted by default. A Deny-only request offers no allow button. A runtime smart denial can offer only a one-operation override and Deny, or Deny alone. Explain the available scopes alongside the buttons: Once permits this operation; Session and Always name the runtime's patterns they cover, every command matching one of them and not this one alone, for the native session or, with Always, persisted in the native profile. The runtime names those patterns whenever it offers Session or Always. Allow for session and Always allow each ask for confirmation, so a tap that lands on a wider scope when the list moves grants nothing: the dialog repeats the patterns and, for Always, where its grant is revoked (Hermes: removing the entry from the profile's `command_allowlist` in `config.yaml`); the app itself does not list or revoke grants. Display the full command and reason without shortening them to fit. Other, custom text and Skip are information-question controls and are unavailable here.

Submission targets the exact pending native request, without sending `/approve` chat text or starting a new turn. For these structured controls, the bridge requires the host's own person, who must also own this conversation, on a still-paired device, and sends approval metadata to no one else: anyone else sees the readable message, which names the offered actions and says only the host's person can answer. The bridge signs each decision it passes on with a key of its own that no sandbox reads, and the agent's channel acts on no unsigned, altered, replayed or stale decision, so a program in the sandbox cannot approve its own command by speaking for the bridge. Runtime approvals are decided with a paired device's buttons alone: typed approval commands (`/approve`, `/deny`, `/yolo`, `/approvals`) are refused by the bridge from everyone, the host's person included, and neither stored nor relayed, and the channel answers any that reaches it itself. This is runtime consent, separate from the sandbox policy inbox: enclos's policy remains in force, and the runtime owns grant persistence and execution. The [runtime approval protocol](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#runtime-approvals), [enclos ADR 0053](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0053-runtime-approvals-use-exact-native-requests-and-explicit-scopes.md) and [enclos ADR 0060](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0060-the-bridge-signs-runtime-approval-decisions.md), both proposed, define that authority, the signed decision and the exact-request contract.

Controls are disabled while offline, awaiting a receipt, uncertain or terminal. Show the confirmed **Allowed once / Allowed for session / Allowed always / Denied** action, or **Expired / Cancelled**. A native decision made elsewhere may report only **Resolved in the runtime**: explain that its decision detail was not received, rather than inventing allowance, denial or scope. Acceptance confirms consent only, not that execution started or succeeded. Canonical broadcasts update the card but do not acknowledge this device's request. Lost replies and ambiguous errors require fresh reconnect sync before another explicit decision; no action, including Deny, queues or resends automatically. A closed card never reopens or addresses the next native request.

Approval metadata, state and message links use the existing host-scoped question cache, retaining immutable definitions and newest confirmed revisions across background loads, history sync and app restarts. Clear cache and Forget this host remove the local copies. Old question records remain compatible. An older app displays the readable message, which decides nothing. This needs updated app, bridge, channel and supporting Hermes APIs.

There is no typed fallback. An approval no card can show (one the bridge refuses, one outside the protocol's bounds, or a bridge or runtime without the capability) arrives as text that shows the whole command and says the app cannot decide it; the channel denies it at once where the runtime resolves its exact request, and the runtime's timeout denies it otherwise. In a bridge-managed group, the buttons target the requesting member directly.

This behaviour is specified once for Android and iOS. Android uses Compose buttons, selectable wrapped command text and a Compose confirmation dialog for Allow for session and Always allow; iOS must use native SwiftUI controls with the same offered scopes, consent rules, exact receipts, terminal states, host-scoped cache and readable text for an approval no card shows. Android is built; iOS is not built yet.

### Files

An agent's message may carry files: an image it made, a chart, a document (enclos `docs/protocol.md`, Files). The app fetches each from the bridge over the conversation's connection, in parts, when the message is first shown: on an unmetered network (Wi-Fi), any file up to the bridge's 25 MiB; on a metered one (mobile data, a hotspot, as the phone's system counts it), a file above 10 MB only when tapped, so an agent cannot make the phone pull it over mobile data unasked, and by itself once the phone is on an unmetered network again. With no network, or before the system says, the network counts as metered. It keeps each in its cache (never backed up), in a folder per host and file; a file whose id is not of the bridge's form (letters, digits and `-`, as a UUID) is not kept. Tapping an available file opens its viewer in the app, with Back, its name and Share. Sharing starts only from that explicit action. A file that did not come says why and is fetched again when tapped: a fetch the connection broke, a part out of order, or a file the phone could not write (storage full); it goes on from where it was. A cached file cleared by the system is fetched again when tapped. A message with files and no words previews as "Image", or the file's name.

An image in a format the phone decodes (PNG, JPEG, GIF, WebP, HEIC or HEIF, BMP) shows in the bubble, above the words, decoded at the screen's size, in a box of its own shape held between 1:3 and 3:1, the image fitted inside; any other image type (SVG, TIFF, AVIF), or an image that fails to decode, shows as a file line instead, which opens the document viewer with its notice and Share; tapped, it opens full screen, edge to edge, on near black in both themes (as photo viewers do: the image is the only colour), with Back, its name and Share over it on a shade, which a tap on the image hides or shows. Pinch zooms it, up to 6×, around the fingers; while zoomed it moves with a finger, its edges held at the screen's; a double-tap zooms 2.5× on that point, or back to the whole image. It is decoded at up to 4,096 px on its longest side, to stay sharp when zoomed; an image is never decoded above 64 MB in memory, a smaller sample being taken (Android draws no bitmap above 100 MB), and one that would still be larger shows as a file line.

Other files show as a line with their name and size. HTML opens as an artefact as described below. A PDF (`application/pdf`) opens in a native, read-only document viewer with scrolling and zoom ([ADR 0008](adr/0008-pdfs-open-in-a-native-viewer-with-isolated-rendering.md), proposed); external PDF links and form filling are disabled. Other text (`text/*`, excluding HTML, plus `application/json` and `application/xml`) shows literally as selectable UTF-8 text, without running content or fetching resources, up to 1 MiB; it is drawn in blocks of at most 4,096 characters as it scrolls into view, so a large file is never laid out at once (a block ends after a line break when one fits; a block that goes on with a line too long for one starts with a faint arrow, outside the selection, so the cut does not read as a line break). Media types choose the viewer; a filename extension alone does not. An unsupported format, invalid or oversized text, password-protected PDF or failed PDF preview shows a notice inside the viewer, with Share, and **Open in another app** when the file may be opened elsewhere (below), still available. No failure automatically hands the file elsewhere. Android is built; iOS follows the same behaviour with its own native viewer when implemented.

**File names** are the agent's: a file's name, wherever it is shown (its line, a viewer's bar, an image's description, a conversation's preview, the label handed to another app), drops hidden characters (controls, bidirectional overrides and isolates, zero-width and other default-ignorable characters, tag characters and blank fillers; a joiner or emoji variation selector stays only between two non-ASCII characters: the same rule as enclos-protocol's `visible` module), so `invoice`, U+202E, `fdp.apk` cannot read as `invoicekpa.pdf`. The file is kept under a name of letters, digits, `.`, `_`, space and `-` only, without a leading dot and at most 80 characters, a longer name shortened before its extension so the extension stays. Android is built; iOS follows the same rule when implemented.

**Share** hands that one original file to another app through the system's share sheet. The document viewer also offers **Open in another app**, an explicit handoff to a compatible app, only for a file another app may be asked to open ([ADR 0008](adr/0008-pdfs-open-in-a-native-viewer-with-isolated-rendering.md)): its media type is on a fixed list (PDF, plain text, CSV, Markdown, common photo, audio and video formats, and office documents) and its name ends in one of that type's extensions. The agent chooses both, and another app may read the type back from the name's extension, so a type a browser or installer would run (HTML, XHTML, SVG, XML, JSON, an APK) or a mismatched extension (`page.xhtml` as `text/plain`, `invoice.pdf.apk` as `application/pdf`) is never opened elsewhere: such a file offers Share only. Both actions go through the system's chooser, so the person sees which app gets the file. Android uses `ACTION_SEND` for Share and `ACTION_VIEW` for Open in another app, each in `Intent.createChooser`, with a read-only grant for that attachment's cached `FileProvider` URI. A missing cached file, unavailable handler or refused launch produces a notice; if the cache was cleared while the viewer was open, close it and tap the file to fetch it again. The receiving app handles the file outside this viewer's controls. These actions use the existing attachment cache and protocol; no bridge or runtime change is needed.

**Static HTML artefacts.** A self-contained UTF-8 HTML attachment opens as an artefact ([ADR 0005](adr/0005-static-html-artefacts-open-in-a-separate-viewer.md), proposed). An attachment whose media type is `text/html` has a card with its name and size that offers to open the page; a `.html` name alone does not make another media type an artefact. The viewer fills the screen, with a native bar for Back, its name and Share, and a scrollable page below. Loading and a failure to read the page are shown there; Back and Share stay available. A page larger than the attachment limit of 25 MiB or with invalid UTF-8 is refused. Share first asks: the app chosen shows the original HTML file its own way, may run scripts it holds and load what it links to, outside this viewer's controls.

The page may use HTML, inline CSS and data images or fonts. JavaScript, storage, network requests, file and content access, forms, automatic outgoing navigation and native bridges are unavailable; relative resources do not load. A link to an anchor in the same page may scroll there. A tap on a main-frame `http` or `https` link first shows a sheet with the destination's host as the network spells it (punycode, so a look-alike name in another script shows as `xn--…`) and its whole address, non-ASCII percent-encoded, in a box that scrolls; an address longer than 2,048 characters once encoded is not opened, and a notice says so; **Open** hands it to the same browser as a conversation link, **Cancel** stays. The private page stays in its viewer. The sheet is there because a page decides what a tap lands on (a link can cover the whole page) and its address can carry anything the agent wrote into it, which then leaves the phone outside the sandbox's network policy. Subframes, redirects, navigation without a user gesture and other schemes are meant not to reach the sheet (see To verify). The opened website uses the browser's normal network access, cookies and site permissions, outside the private viewer's controls. The private page receives no keys or app state. These controls are written for Android; platform probes remain in [To verify](#to-verify). HTML in message text stays literal, as above. Interactive pages, external assets and multi-file sites are not part of this version. The file uses enclos's existing attachment delivery, cache and ownership checks; there is no separate artefact service or history.

The runtime's plugin tells the agent what the app draws, so that it formats when it helps (Hermes: the plugin's `platform_hint`, in enclos).

An initial static-viewer probe on an Android 17 / API 37 emulator, Google WebView 145.0.7632.218, rendered inline CSS, Unicode text and an embedded data PNG. The script did not execute; a frame reported `ERR_BLOCKED_BY_CSP`; external styles, images, frames and script fetches never reached a local request counter that a separate emulator request proved reachable. Form submission and file/content link taps left the page in place. The browser-link handoff and remaining platform probes are listed below.

## 6. Motion

Short and functional, never decorative: something moves to show where it came from or went. Durations: 150 ms for a change in place, 250 ms for a screen or a message arriving, 150 ms for what leaves. Arriving decelerates, leaving accelerates.

- A full screen arrives over the tabs: it slides in from the right edge, opaque, while the tabs drift a tenth of the width to the left under it. Going back is the same move reversed: the screen slides off to the right, uncovering the tabs drifting back. Both take 250 ms at an even pace, so a finger can drag the move: with the back gesture the screen follows the finger and goes or returns where it is let go.
- The Inbox and Agents views slide side by side with a horizontal swipe; tapping their switch slides to the chosen view in 250 ms.
- A message fades in while the others slide up; an agent that moves to the top of the inbox slides there with its conversations, and those it unfolds fade in.
- Badges, chips, pairing steps, the send button and the theme change smoothly.
- An agent at work: its avatar's corners swell out of it and fade, every 1.4 s; the working wave beside it.
- With the system's animations turned off, transitions end at once, the working wave stands still and an avatar does not pulse.

## 7. Theme

Light or dark: the system's setting by default. Once the person chooses (System · Light · Dark, in Settings, Appearance), the app keeps their choice on this device until they choose System again. Switching crossfades the colours; the screen is not rebuilt. The colours are the design system's tokens, the same in both apps.

## 8. On the phone

- **Keys**: the device's signing key is made in, and never leaves, the platform's key store; the Noise key is wrapped by it.
- **Stored**: the paired hosts (each bridge's address and key, the device's id there, the wrapped Noise key), the last message read per conversation, the theme, whether the app lock is on.
- **Conversations are kept on the phone**: each host's agents, the conversations, their names and archived state, every message with its files' descriptions, and the steps of each answer. They show when the app opens, before any connection, and while a host is unreachable; a sync then brings only what is newer. The copy is read off the main thread, in two passes: first what the first screens show (every conversation with its last message, and the last 40 messages of the 10 most recent), with the launch screen kept until then (at most a second) and the connections opened after it; then every other message, merged in. Until that second pass ends, search and unread counts see only the first pass's messages. The bridge stays the source: what the phone keeps is what the bridge sent, and a conversation started on the phone is kept once the bridge confirms it. Pairing again with a host forgets what it sent before. A message that cannot be written (a full disk) leaves no gap: no later message of that host is kept until the app starts again, so the next sync, which starts after the newest message kept, brings it back. A kept row the app can no longer read is skipped, not fatal. A conversation is known by its id: one that a host's bridge sends with the id of another host's conversation is ignored. The copy is in the app's private storage, readable by the app only, and not encrypted by the app itself: it is as safe at rest as the phone's own storage encryption makes it. Files stay in the cache, which the system may clear: they are fetched again when shown.
- **Nothing leaves the phone** ([ADR 0003](adr/0003-nothing-of-the-app-leaves-the-phone.md)): no backup, no transfer to a new phone. A new phone pairs again.

### App lock

For a phone lost or left unlocked: with the app lock on, the app asks the person to prove it is them, with a strong biometric the phone has (fingerprint, or a face unlock the phone rates as strong; a weak face unlock, which a photo may fool, does not count) or else the phone's own screen lock (PIN, pattern, password), when it opens and when it comes back after a minute or more in the background. Until then the app shows only a lock screen (the mark, "Enclos is locked", and Unlock): nothing else of the app is drawn, so no screen, dialog, sheet or menu left open is there to see or reach, by touch, keyboard or accessibility services, and no message is marked read. Once unlocked, the app is back on the screen and the place the person left. Back leaves the app. The prompt shows on its own as the app opens and each time it comes back locked; after a cancel, Unlock asks again, and the lock screen says what the system said (cancelled, too many attempts). While the lock is on, the app's window is secure: screenshots, screen recordings and casts show nothing of it, nor do the recent apps.

It is off until the person turns it on in Settings, Security, which needs a screen lock on the phone (else Settings says to set one) and asks to unlock once, so a lock that cannot be opened is never set. Turning it off asks to unlock too, so someone who picks the phone up in the minute after it was put down cannot turn it off. A phone whose screen lock is removed has nothing left to unlock the app with: the lock then turns itself off as the app opens or comes back, rather than lock the person out, and Settings says so. It hides the app; it does not encrypt what the phone keeps, nor tie the keys to it: the conversations and keys are as safe at rest as the phone's own storage encryption and key store make them, and the connections stay open behind the lock, so messages keep arriving.
