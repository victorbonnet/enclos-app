# enclos app: what it does

The enclos app is a channel to the agents of a person's enclos hosts: from a phone, over their tailnet, they list each host's sandboxes and agents, talk to any of them, and read what an agent sends on its own, such as a cron job's output. enclos's side is in its design: [ADR 0042](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0042-a-bridge-on-each-host-serves-the-mobile-app.md) (a bridge on each host), [ADR 0043](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0043-sharing-an-agent-is-not-hosting-it.md) (sharing) and `docs/protocol.md` (the device leg), all proposed. The plan is in [enclos#145](https://github.com/victorbonnet/enclos/issues/145).

This file says how the app behaves, on every platform. Android is built; iOS is not started. **Both platforms behave the same and each looks native**: a behaviour here holds on both, and the [Platforms](#platforms) table says how each renders it. A pull request that changes a behaviour changes this file; a decision that is hard to reverse gets an ADR in `docs/adr/`.

Three kinds of statement are kept apart, as in enclos: what is decided (this text, an accepted ADR), what is proposed (an ADR with `status: proposed`), and what is still [to verify](#to-verify). Nothing here describes security behaviour as tested unless a test or a probe shows it.

Words are enclos's ([GLOSSARY.md](https://github.com/victorbonnet/enclos/blob/main/GLOSSARY.md)): host, sandbox, agent, runtime, channel, and for the app, bridge, person, paired device, conversation.

## 1. Shape

- **One Rust core, a native app per platform** ([ADR 0001](adr/0001-one-rust-core-and-a-native-app-per-platform.md)). The core (`core-ffi/`, over enclos's `enclos-protocol`) does the protocol's cryptography: pairing links, the Noise handshake, sealing and opening messages, and push previews. Each app does everything else natively: screens, the connection, storage, keys.
- **Hosts are independent.** The app pairs with each host's bridge on its own and gathers their agents into one list. No host knows of another.

## 2. Pairing

1. On the host, `enclos app pair` shows a QR code and a link (`enclos://pair?…`) that works once, for 5 minutes, while `enclos app serve` runs.
2. The person scans the code, types or pastes a link, or taps it wherever it is: the app opens on any `enclos://pair` link. A chat or a note opens only https links, so `enclos app pair` also prints `https://<bridge>/pair#…`, a page of the bridge whose "Open in enclos" opens the `enclos://pair` link (enclos `docs/protocol.md`, Pairing); pasted in the app, that https link reads as the other, but only when its own address is the bridge address it carries (as the bridge prints it): one that names another address is refused, since the person checks the address at the start of the link. The app reads the host's name, its bridge's address and the link's expiry, and shows them with a countdown. The address is the bridge's host name and port only: a link whose `url` holds a path, a query or no host name is refused, so what is shown is where the app connects. A link that is not a pairing link is refused with the app's own reason, never the link's text. A tapped link pairs only once the person confirms ("Pair with <host>?", Pair or Not now), since any page or message can hold one; a link opened while a pairing goes on is ignored, and so is one opened before (the system hands it again when it restarts the app, after an update): such a link can still be typed.
3. The app makes the device's signing key in the platform's key store (StrongBox where the phone has it) and a Noise key pair, wrapped by the key store.
4. It connects, sends a pairing request (its model name, its public key, a proof from the link's code, and its signing key's signature for pairing on this connection), and shows the terminal's question: `<model> (tailscale login: <your login>) wants to pair. Accept? [y/N]`. The person answers in the terminal; the app shows Paired or why not (refused, or the connection ended). A pairing that ends unpaired deletes the signing key made for it.

The pairing screen has three steps, always in this order: code read, device key made, accept on the host. Its copy states what happens, never how safe it is.

**A link naming a host already paired.** A pairing link gives the host's name itself, so a name proves nothing; the bridge's key, which the Noise handshake checks, tells one bridge from another. When the link names a host this phone is already paired with:

- **Same bridge key**: the app pairs again, as for a new host. Once the bridge accepts, the new pairing takes the old one's place and the old pairing's device key is deleted from the key store; what the host sent before is forgotten, as for any pairing again ([On the phone](#8-on-the-phone)).
- **Another bridge key**: the app makes no key and does not connect. It shows a card, "Replace <host>?", with the paired bridge's address and the link's. **Keep <host>** leaves the pairing as it was. **Replace** pairs with the link's bridge; once it accepts, the old pairing, its device key and what the app showed of that host are gone.

The replaced host still lists this phone as a paired device until it is removed on that host.

**A pairing that is not accepted** (refused, the link expired, the connection ended, the key could not be made) deletes the device key it made. The keys are made off the main thread, and a failure to make them ends the pairing with its reason.

## 3. Connection

- The app opens a connection to each paired host when it comes to the foreground, and keeps it while the phone lets it.
- Pairing and authentication sign the protocol's distinct purpose labels followed by the connection's handshake hash, through the shared Rust core. A signature for one purpose cannot authenticate the other.
- A connection that ends while the app is in the foreground is opened again after 2 s, then 4, 8, 16, 32, then every 60 s, until it is authenticated. Reconnect in Settings tries at once.
- On each connection the app asks for the host's agents and syncs the messages after the newest one it [keeps](#8-on-the-phone) from that host (every message, the first time); the bridge sends each message with the time it was stored.
- In the background the app does not connect. With push on, it closes its connections when it leaves the foreground, since a host pushes only to a person with no device connected; without push, a connection already open stays up while the phone lets it. What arrives meanwhile is shown at the next sync, and announced by a [notification](#notifications) when push is on.
- When the bridge reports an error (an agent it could not reach), the conversation and Settings show it, in the bridge's words.

A message from the bridge that the app cannot use is answered as enclos [`docs/protocol.md`](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#messages) (Messages) says. A `v` other than 1, the version the app speaks, is answered with an `error` of code `version`, and the connection ends, saying whether the app or enclos on the host needs updating. Anything else leaves the connection open. An unknown `type` gets `unknown_type` and is otherwise ignored, so a newer bridge can send optional messages; the types the app knows are enclos-protocol's list of what a bridge sends a device, which a test checks. A message the app cannot read (not JSON, no `v` or `type`, a field missing or wrong, as from another version of `enclos app serve`) gets `bad_message`, naming its `id` when one can be read, and is skipped. An `error` is never answered, so the app and the bridge never trade them. The host's row in Settings and its conversations then say that a message was skipped and why, and to update the app, until Clear cache, Forget or the app's next start. A skipped history message is not fetched again once a later one is kept, since each sync starts after the newest message kept: for one, the notice also says to Clear cache, which syncs everything again. A frame that does not decrypt still ends the connection, as the protocol says. While pairing, an unknown `type` is answered the same way; an answer the app cannot read (not JSON, say) ends that pairing.

The connection's state is the app's own: it is connected only once the bridge says `authenticated` over the Noise session, never because of what a close reason or an error says.

### Notifications

A host's bridge pushes to the phone when an agent's message, a question, a runtime approval or a newly held task arrives while none of the person's devices is connected (enclos [`docs/protocol.md`](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#notifications), Notifications; enclos ADR 0065, proposed).

- **Push is on** only in a build given Firebase's settings, and with them the host's user given that project's key (`enclos app push key`); a build without them asks Firebase for nothing ([ADR 0010](adr/0010-firebase-settings-come-from-outside-git-and-push-is-off-without-them.md), proposed).
- **The token**: the app gives each host its FCM token in the pairing request, at each connection, and at once to each host connected when the token changes. It keeps the token with its Firebase project, and gives none from a build with push off or made for another project. A phone with no token yet (no Play services, no network as the app started) asks again when a host next connects.
- **What it shows**: the push carries the preview sealed for this phone. The app opens it with the push key of each host it paired with; a push that none opens, or one whose `seq` is not newer than the last shown in its conversation, shows nothing, and what the app could not read is logged without its content. A push for another conversation shows whatever order FCM brings them in. The notification's title is the agent; its text is the preview's words without the markdown's marks or hidden characters, at most 120 characters, or "New message" when there are none. With the [app lock](#app-lock) on, the text is always "New message", and turning the lock on takes away the notifications already shown. On the lock screen the text follows the system's setting: with "hide sensitive content" on, it says "New message"; with Android's default, the whole notification shows.
Push previews for questions, runtime approvals and newly held tasks start with **Needs you:**; normal notification privacy settings still apply.

- **One notification per conversation**, replaced by the next, and **one channel per agent and host**, named "`<agent>` on `<host>`", so the person can silence one agent in the system's settings.
- **Tapping it** opens the app on that conversation of that host, once the phone holds it (after the sync the connection starts, for a new one); going anywhere else first drops it. Opening a conversation takes its notification away.
- **Forgetting a host**, or pairing it again, takes away what the phone showed of it: its notifications, its agents' channels, and the last `seq` shown in each conversation (a bridge paired again may count from the start).
- **The permission**: on Android 13 and later the app asks once to show notifications, when push is on and the first host is paired. A push it may not show is not counted as shown.

Not built: the Reply and Mark read actions; fetching the message in the background (it comes with the next sync); telling the person, in the app, that its notifications are off in the system's settings.

## 4. Screens

**The bars.** Every top and bottom bar is the same material, full-bleed, with no shadow and no hairline at the edge where content passes: on Android 12 and later the content behind it is blurred (20 dp; 12 dp while the conversation or the chat list is being scrolled, back within 150 ms of it stopping) and tinted with `bg` at 0.76, so what passes under the bar is seen through it; before Android 12 the bar is `bg` and fades 20 dp into the content. The content behind a bar keeps its own room — the conversation's messages sit 8 dp below the name bar and 12 dp above the composer at rest — so nothing that is not moving is ever behind glass. The material is the bar's edge; where nothing passes behind it, the bar is the page. The screen is edge to edge: a top bar's material fills the status bar's room and a bottom bar's reaches the screen's bottom edge, filling the navigation bar's room, while the bars' controls stay clear of both; a screen with no bottom bar keeps its content above the navigation bar at rest, and lets it scroll under it. A bar's own controls draw only `text` and `textMuted` on it; anything faint, accented or inverted sits on its own fill.

**The first screen** has two views, the conversations (the [inbox](#inbox)) and the [agents](#agents). Its top line holds the switch between them (a pill with the conversations' bubble and the agents' glyph, the one shown on `surface`), then, on the conversations, unread only, and Settings' gear. Swiping left on the main content opens the agents; swiping right returns to the conversations. The content follows the finger and settles on a view when released; there is no wrapping at either end. The switch shows the view a swipe would settle on and can still be tapped; the actions on the top line and the search field's label change once the swipe has settled. Vertical swipes scroll the current list. Over the end of the view, on the bars' glass (a fade to the ground on Android before 12), sit the search for that view (a pill on `surface`: "Search conversations", "Search agents") and the compose button, which opens a [new conversation](#new-conversation); both show once a host is paired, and stay in place while the views slide, with the same search text across both. Back from the agents view leads to the conversations. Pairing a host lands on the agents.

**Full screens** arrive over it from the right: a conversation, an [agent's page](#an-agents-page), a [sandbox's page](#agents), a new conversation, [Settings](#settings), pairing and a policy request. Back from each leads to the first screen, except an agent's page opened from its sandbox's page, which goes back to that page, and a conversation, or the new conversation screen, opened from a policy request (to ask why, or its own conversation), which goes back to the request. The app is in portrait only, for now, the QR scanner included.

**The first screen under a full screen.** While a full screen covers it, the first screen stays as the person left it, and Back (the arrow, the system button or the back gesture, its preview included) returns to that place, not to the top: each view keeps its own place — its first row and pixel offset —, the view settled on, the shared search text, and the Inbox's filters, and the list is already there when it shows again, with no jump and no repair. A place is kept by position, not by row: rows that change order above it while it is covered (a reply moving its agent to the top) leave the same position showing another row. Under a search, the matches are found again over the messages before the list shows a row, instead of the empty-result line showing first and taking the place. Only the first screen is kept so, and only as itself: nothing is kept per conversation, so opening and leaving them leaves nothing behind, and a detail page or a conversation opens at its own usual opening place rather than at an earlier scroll. The platform saves that same state, so a rotation, or the process killed and restored, comes back to that place too (see To verify).

### Inbox

**Needs you comes first**, above Groups and Agents in both active and archived Inbox views. It lists questions, pending runtime approvals, held tasks and pending, applying or failed sandbox policy requests from every paired host, newest first. Each compact row uses the conversation rows’ layout: a top-aligned 32dp avatar, neutral agent name and muted relative age with a chevron on the first line, then a single muted preview line with the host and short explanation. Expired stays beside the name; offline previews identify cached requests. Text styles, spacing and truncation match the surrounding conversation rows. Tapping opens a focused request sheet. It offers the request's native action, **View conversation** when its exact conversation is kept, and **Dismiss reminder** in a consistent secondary button style. Held tasks offer **Resume task** only when the runtime permits it, plus **View task** for the description, comments and history; from a bridge that takes answers, the sheet leads with the agent's decision and its answers instead ([Held tasks](#held-tasks), Answer from Needs you), and an answered task leaves the list, as does a held task whose runtime says it waits on the team rather than on the person. Policy requests offer **Review request** to open the full consent page. A missing conversation never opens another host's history. The section appears while requests, refresh errors or dismissal errors exist and stays unfolded. Unread-only and archive filters do not hide requests; search matches their summary, agent or host. [ADR 0012](adr/0012-needs-you-combines-requests-without-changing-their-authority.md) records replacing Sandbox requests.

**Reminder dismissal.** Dismiss reminder hides this exact reminder for the paired person on this host, persisted by the bridge and shared across their devices. It never answers, approves, denies, resumes, cancels or edits the underlying request. It is online only, requires a fresh indexed source version and waits for an exact correlated host receipt or a complete host snapshot before disappearing. A changed held-task revision or policy revision/state appears again; an unanswered question's timeout alone does not. Empty authoritative snapshots and covered canonical policy generations are cached as authoritative. On a failed refresh, a new live policy id or revision/state still appears through canonical fallback, while a generation covered by the last successful snapshot stays omitted. An unreadable cache row is deleted and logged without losing history. Discovery freshness does not gate native question answers or runtime approvals, which retain their own capability and native-sync checks. The legacy `question.close` wire message remains compatible; current question cards offer only Dismiss reminder for discovery dismissal.

The Inbox switch and each agent's row in Agents show a count while requests wait. In Agents and sandbox pages, the agent name has its own full-width first line with a chevron; Needs you starts the second line, followed by activity. Usage appears below in smaller muted text. Metadata wraps at word boundaries within the text column instead of taking trailing columns that squeeze the name and activity. Counts use one item per host, kind, agent and original id. A host's complete snapshot replaces only its own rows, including an empty result; partial or failed refreshes retain the last known list. Offline rows say they are cached. A failed refresh shows a notice even with no cached rows, so failure does not look like zero requests. Reconnect resets that connection's revision sequence. Another device's answer, resume, decision or close removes the row on the next live snapshot or sync. Clearing cache and Forget this host clear local rows. These are discovery references: original controls recheck their own connection, revision and authority. If a connected host cannot provide compatible native controls (such as an independently scoped runtime approval), the focused row explains that controls are unavailable and points to the original message or runtime instead of repeatedly asking the person to reconnect.

An ordinary question that expires unanswered stays listed as **Expired**, read-only. Its historical choices are plain text; there is no answer field, reply draft, answer button or skip button. **View conversation** and **Dismiss reminder** remain available in the request sheet. Dismissing removes only the reminder after the host confirms; native state stays expired. Pending questions retain **Send answer** and **Skip question**. Expired runtime approvals also offer no response controls.

By agent, within the selected active or archived view: one row per agent with a matching conversation, the agent with the newest matching conversation first. In the active view, only its conversations with something unread show under it while folded, so a new message is one tap away without the list growing with every conversation. The archived view shows all matching conversations expanded.

Direct conversations, including Home, are hidden from both inbox views, search and inbox unread counts only when their agent is absent from that host's inventory **and the host confirms it removed**. A missing channel, missing token or `agent rm --keep-data` does not establish removal: its history remains readable in the inbox, including with an older bridge that cannot confirm removals. Hidden history and read positions stay saved and reappear if that host lists the same agent again. Going offline does not discard the inventory or confirmation already received; a new connection refreshes removal confirmations, and a restart shows saved history until a fresh confirmation arrives. Equal names on another host and group conversations stay independent. [ADR 0011](adr/0011-confirmed-removals-hide-conversations-without-deleting-history.md) records the visibility and host-page cleanup decision. Android implements this; iOS follows the same rule when built.

**An agent's row** shows its avatar (its initial inside the logo's corners, in `accent` while its host is connected, pulsing while it works), its name, the time of its newest message in any conversation (today: `07:12`, this week: the weekday, else `3 Nov`), and its [Home](#home)'s last message (words without markdown on two lines at most, the person's own prefixed "You:") with Home's unread count. While the agent works, the wave and what it does take the message's place, with where when that is not Home (`· in Weather in Lyon`, `· in 2 conversations`); while only its runtime says it is at work ([agent activity](#agent-activity-and-tasks)), the wave and what it is doing (`working on a task`). Tapping the row opens Home.

**What is folded** is said at the end of the agent's group, on a line of its own starting where its conversations do, in `accent`, with a chevron pointing down: `17 conversations`, or `15 more conversations` when some show already. Tapping it unfolds them all, newest first, and the line, now at the end of the list, says `Show less` with the chevron pointing up. An agent stays unfolded while the app runs; with nothing folded away, there is no line.

**A long press on an agent's row** (with a haptic tick) opens its menu under its name: **New conversation** with it (while its host still lists it), **All conversations** or **Fewer conversations** (as the line above, when some are folded away), **Routines** when its runtime supports them, and, under a line, **About** the agent, its page.

**Sections fold.** The Groups and Agents headings each fold their section away, or back, when tapped: the name, small and faint with no line under it, and a chevron at its end, pointing down while open and right while folded, turning between the two. A folded section shows its unread count by its name. What is folded stays so across starts of the app; a search shows all it finds, with the headings unfoldable meanwhile.

**A conversation under its agent** starts where the agent's name does, without an avatar: its [name](#names) ("No name yet" while it has none), the time of its last message, an "on its own" header when the agent sent it unprompted, the last message's words (or, while the agent works on it, the wave and what it does), and the unread count. A conversation with no message is not listed (one left empty, here or on an earlier version of the app). With no conversation yet, it points to the compose button. With no host paired, the inbox says how to pair one.

**A task under its agent.** Under an agent the active Inbox lists, a branch before its conversations shows the first task named by its activity that the phone keeps: the task's title on one line, its task status and a chevron. It stays visible while the agent's conversations are folded; tapping it opens the task's [sheet](#a-tasks-sheet). It leaves when the activity no longer names it. Search, the archived view and Unread only omit this branch. While the branch shows, the agent's preview uses Home's last message, unless it is working in a conversation; its avatar and working indicator stay active, and its row still opens Home. Android implements this; iOS is not started.

**Search.** The search at the bottom finds conversations by their name, their agent's address, and what was said in them (the agent's messages as their words, without markdown), whatever the case and the accents; with several words, each must be found, in the name or in any of its messages, not necessarily the same one. A conversation found by a message shows that message, the newest that holds the most words, in place of the last, with the words in `accent` (Home's, on its agent's row). Search reads every message, so it runs off the main thread, each message's words worked out once while the app runs. While the next search completes, the previous matches stay visible only if their conversations remain eligible for the current view and filters; the first search waits with no matches instead of briefly showing every conversation. While searching or showing unread only, only agents with something found show, and everything found shows under them, folded or not, with nothing to unfold. Nothing found says so.

**Filters.** One Filters button on the title's line opens a menu with two independent toggles: **Unread only** and **Archived conversations**. It appears in Inbox when a host is paired. Both start off, showing all active conversations. Unread only limits the selected active or archived view to conversations with something unread; selecting both shows unread archived conversations. Changes apply immediately, and the menu stays open while toggling so both options can be adjusted together. The selections stay when switching between Inbox and Agents, and when Back returns from a full screen opened over the first screen. With either toggle on, the button uses `accent` and a subtle accent surface, and its accessible state names each filter that is on ("Unread only", "Archived conversations", or both); with both off, it uses `text-muted` and its state says no filters are active. There is no filter by agent, since the inbox is by agent already.

### Archived conversations

The Inbox starts with active conversations. Turning on **Archived conversations** in Filters selects the archived view; turning it off returns to active conversations. Search and unread-only filtering remain available within the selected view. Policy requests appear only in the active view; groups remain their own section in both views. An archived conversation keeps its identity and every message, file description, name, read position and group member. The Archived view can find it by the same names, addresses and message text as the active view; **Unarchive** restores that same conversation and history ([ADR 0006](adr/0006-archived-conversations-are-a-restorable-inbox-view.md), proposed).

**Archive** is available from a direct or group conversation's actions and its long-press menu. Home cannot be archived and offers no **Archive** action; an ordinary conversation named Home can still be archived. Archived conversations, including a Home archived by an older version, offer **Unarchive** instead. Both actions require the host to be connected; while offline the disabled control says `Connect to <host> to change archive state.` While waiting it says **Saving archive state…**; with no answer from the host within a minute, it stops waiting and says to reconnect and check the archive state before trying again. Nothing is queued offline or hidden optimistically: the list changes when the bridge sends the new metadata. The bridge owns this state and sends it to the person's other paired devices and at every sync, so reconnecting, clearing the phone cache or pairing another phone restores the same archived state.

Conversation metadata carries the bridge's revision; the phone keeps the highest it saw for each conversation and ignores a lower one, so a delayed broadcast cannot undo a newer archive, name or read state. Revisions assume a bridge's database is never reset or restored from an older copy: after that, a reused id (a Home's) keeps its older state on the phone until the person clears the cache. The phone keys conversations by id. A Home's id, `home.<sandbox>.<agent>`, is the same on two hosts that both have that sandbox and agent: the phone keeps the first host's and leaves the second's out, with its messages, typing, tool steps and group state, rather than mixing them or letting one replace the other. The second host's heading in Agents says how many of its conversations are not shown and names each affected agent (`sandbox/agent`) and the other host holding it — at most two other hosts, then how many more — and that agent's page says its Home is not shown here and which host holds it. When it knows no affected agent, or the holding host is no longer paired, the notice says only that another paired host has an agent with the same sandbox and name, whose conversations use the same ids. Showing both needs the cache keyed by host as well (see [To verify](#to-verify)).

Archived conversations contribute no preview, newest-message ordering or unread count to the active Inbox and its folded-section counts. An agent with no conversation in the selected view is absent. Its header opens Home only when Home belongs to that view; otherwise it is a heading for its matching conversations, with no Home preview or tap target. Their stored read positions remain intact; opening one marks it read by the ordinary rule below. A new reply, status line or cron output stays in that archived conversation and leaves it archived. Direct and group conversations use the same actions. Archiving leaves running work and group discussions alone, and agents stay available in Agents. It calls no runtime archive command, resets no context and removes no saved memory: Hermes and a future OpenClaw channel share this app behaviour through enclos's conversation protocol.

### Deleting a conversation

Active and archived direct and group conversations offer **Delete** in their long-press menu and their open conversation's actions. A confirmation explains that the conversation, history and files are permanently removed from the host and paired phones, and running work is stopped. Home has no Delete action and the host refuses its deletion; a removed agent's Home goes only when the agent is [forgotten](#forgetting-a-removed-agent). Agents and their saved memory and routines stay available.

Delete requires a connected host and stays disabled while pending. An unsent direct-conversation draft offers a disabled action saying `Send the first message before deleting.` The conversation remains visible until `conversation.deleted` confirms removal; an acknowledgement alone never hides it. A failed send, host refusal, disconnect or timeout keeps its history visible and explains how to retry. A bridge that does not know `conversation.delete` answers `unknown_type`, and the app asks the person to update it. The device leg advertises no deletion capability to check first. A development bridge from before victorbonnet/enclos#261 ends the connection on a message it does not know instead, so there a bridge from before deletion reads as a disconnect; no released enclos has the bridge. A restart clears pending command state on the phone; a partially completed deletion remains reserved on the host and can be completed by choosing Delete again. No native deletion is silently resent on restart. A group whose deletion partly completed must retry Delete to finish; its host remembers which native chats remain. Opening a deleted conversation returns to the inbox through the existing missing-conversation navigation.

The phone removes the confirmed conversation's messages, questions, unsent draft, read position, live work state and downloaded files. It stores a deletion record by host and id, and ignores later conversation metadata or live messages for it. Every host sync repeats deletions, including after a cleared cache or on another phone. Enclos's host and runtime behavior is specified in `docs/protocol.md`, Deleting conversations. Android implements this; iOS is not started. Unit tests cover confirmation, failure, retry and host scoping; live phone and sandbox verification remains outstanding.

### Forgetting a removed agent

An agent removed from its host keeps its Home and its conversations saved until the host's person forgets it ([enclos ADR 0067](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0067-the-hosts-person-can-forget-a-removed-agent.md), proposed). Once absent from the host's agent inventory and confirmed removed by the host, its conversations are hidden from the inbox. The host's page keeps **Forget <agent>** available for each agent the host confirms removed, in one **Removed agents** section, using its full sandbox/agent address in the action and confirmation to distinguish equal names. Pending and failed actions stay there until settled or retried. An agent's page already open still says it is no longer listed and, once confirmed removed, that nothing of it is left there.

The page of an agent its host confirms removed has a **Removed agent** section with **Forget <agent>**. Only the host's person sees it: the app asks `agents.removed` of a bridge that lists `agent.forget` in `authenticated.capabilities`, after each authentication, when a live agent inventory arrives, when the host's page opens, and when the page of an agent its host no longer lists opens, and the bridge answers only that person. Until the host confirms the agent removed, such a page says why it offers nothing: the host is not connected, its bridge cannot forget (update it), the app is asking, or the host could not say. An agent removed with `--keep-data`, or one the host cannot tell about, is not listed, so it offers nothing. A confirmation says that its Home and the person's conversations with it, their history and files, are deleted from the host and paired phones; that group conversations it was in stay; and that an agent made again under that name starts with a new Home.

Forget requires a connected host and stays disabled while pending. Each conversation leaves the phone as its `conversation.deleted` comes, as a deletion does ([above](#deleting-a-conversation)), Home included; the host's `ack`, after them, settles the request, removes its action from the host's page and closes the agent's page if open. A failed send, a refusal, a disconnect or a timeout (180 s) keeps the remaining history saved and says how to retry; an answer that comes after a timeout or a disconnect still settles it, and a forget whose agent the host no longer lists after a reconnect is taken as done, as its conversations go at sync. A bridge that does not list `agent.forget` is never asked, and offers no Forget; should one still answer `unknown_type`, the app asks the person to update it. The person's other phones drop the conversations as their `conversation.deleted` comes, or at their next sync when offline. An agent made again under that name has its page again as soon as a new agent inventory lists it, without reconnecting. The host's side is enclos's `docs/protocol.md`, Forgetting a removed agent. Android implements this; iOS is not started. JVM tests cover the request, its receipts, the list and host scoping; live phone verification remains outstanding.

### Home

Each agent has one Home conversation, which its host's bridge makes and keeps (enclos ADR 0044, `docs/protocol.md`, Home): the runtime's home channel. What belongs to no conversation lands there: a cron job that has no conversation of its own, a message the agent sends with no other place to go, the runtime's notices about itself, and the cards of the agent's [held tasks](#held-tasks). It is named Home, opened by its agent's row in the inbox, shown even when empty ("Cron jobs and the agent's notices come here."), and the person may talk to the agent in it too. A cron job started in a conversation still answers in that conversation. Hermes's `/sethome` is answered by its plugin, not run: there is nothing to set.

Home stays active and cannot be archived. A Home archived by an older version keeps the same id, history and delivery route and continues receiving output. It remains available in Archived conversations and from Agents; **Unarchive** restores it to the active Inbox. Opening it still marks its messages read normally; only Unarchive changes that legacy archived state.

**Status lines.** The runtime's notices about itself (Hermes: the gateway online, shutting down, restarting) are not the agent speaking: they come as `status` and show as a quiet centred line, small and faint, with their time, never a bubble. They never count as unread, and the inbox previews the last other message when there is one. The plugin, in the sandbox, chooses a message's kind, so a status line is the sandbox's word, never the app's or the bridge's: it starts with the runtime's name (`hermes: gateway online · 14:02`), is cut to one line, and drops the characters that would reorder or hide part of it. One that carries files shows as a message, so its files show. Status lines coming only from the runtime's gateway, never from a turn, would have to be enforced on the bridge; the app does not.

### Sandbox policy requests

Policy requests appear in **Needs you**, alongside questions, runtime approvals and held tasks, even when they have no conversation. An older bridge still contributes its existing pending, applying and failed policy requests to this list. The request sheet’s **Review request** opens the full policy detail page; the full target, policy scope, reasons and **Approve** / **Deny** / **Close request** controls remain there.

Tapping the row opens its detail page: attempted action, the selectable scope approval writes, who requested it, the exact change the host described, private-address access if requested, and whether all running sandbox work ends for a restart. It links to the originating conversation when one is known, and shows the decision controls at the bottom: below the details and above the navigation bar, never over the details or the top bar. The details scroll under the top bar and stop at the controls; the controls take the height they need, whole, however much of the screen that is, as long as the details keep a minimum of their text between the bars (four lines at the phone's font scale: the implementation's choice, not yet confirmed on rendered screens). Past that (large text, a short window) the controls are given the rest of the room and scroll on their own, in the same order and with the same words, so every control and explanation stays reachable. When the room between the bars cannot hold both that minimum and one whole control (the tallest control as drawn, with the controls' padding), the page is one scroll instead: the details, then the same controls and explanations below them, nothing pinned, added or removed; the person's place in the details is kept when the page changes between the two. A window shorter than one control cannot show it whole in any layout: the page stays one scroll and the control is seen a part at a time; no design covers that size yet. Changing layout never decides, closes or confirms anything: a decision still takes a tap on an enabled control and the screen-lock confirmation. A control's label wrapped by large text makes the control taller, never cut. A pending request the phone can approve also offers **Ask <agent> why**, so the person can hear the agent out before deciding; a failed request was decided already, and an unavailable one can only be closed. It asks the agent that made the request, never another in its place. For a proxy refusal, which has no conversation, it asks the agent of that sandbox with the newest message on this phone, or the first listed when none has one; the page says which, and another can be picked before sending. It opens the request's own conversation when the phone holds it as that agent's direct, unarchived conversation, else the [new conversation](#new-conversation) screen with that agent. The field then holds a question: what the policy does not allow, as the host's `scope` (and the path the agent named, when it led elsewhere), when the host recorded the request (in UTC, whatever the phone's time zone), for a proxy refusal whether this agent or another tried it, why it is needed, and that the person decides; it asks not to look for another way around. Nothing is sent until the person sends it. A draft the person had written in that conversation is kept, and the field says the question was not added; a question the app put there earlier and the person left as it was gives way to the new one, and goes when they leave the conversation without sending it. Asking decides nothing and needs no screen lock: the request stays in the inbox, and Back from that conversation, or from the new conversation screen, returns to it, to approve or deny once the answer is in. Opening the same conversation from a notification keeps that way back. The agent's answer is its own account, not something the host checked. When the phone does not list the agent that asked (removed, or not listed yet) or any agent of a proxy refusal's sandbox, the page says so in place of the link; a new conversation screen restored later without its request or agent returns to the request's page. A file change requiring a restart says **Approve & restart**; unsupported scopes explain why and keep approval disabled. It says approval persists for every agent of that sandbox and updates their policy knowledge for later work. An approval does not automatically retry the attempted action. Network scopes are one host:port; write scopes cover the named path and everything beneath it. The row title and the detail page lead with the host's `scope`, the normalized destination or the writable path with its symlinks resolved, never with the agent's own text over it; when the host resolved a write path through a link to another place, the page also shows the requested path and says approval grants the folder it leads to, not the link. A host that sends no `scope` (before enclos's change) shows the requested target. The agent's action label is shown without hidden characters, and a target's hidden characters are written out (⟨U+202E⟩), never applied. A request the bridge sends without a field the app needs (its id, sandbox, state, time or access) is dropped, never shown and never fatal. Sensitive read denials remain unavailable for approval. Host behaviour is [enclos ADR 0046](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0046-the-hosts-person-approves-sandbox-policy-scopes-from-the-phone.md), proposed; this is a sandbox policy request, not a runtime tool approval.

Only the host's own person on a still-paired device may decide. Approve and Deny each ask for the phone's biometric or screen lock first (the [app lock](#app-lock)'s prompt: a strong biometric or the screen lock), every time and whatever the app-lock setting, so a phone left unlocked in someone else's hands cannot widen an agent's access; cancelled or failed, nothing is sent and the page says what the system said. A phone without a screen lock cannot decide, and the page says to set one. Buttons need a connected host and a completed fresh sync, remain disabled during a decision, and show Saving decision. Nothing is queued offline or optimistically marked approved. A changed policy refreshes the preview; the person must review it again. A request decided on another device shows that result. Completed approvals and denials leave the inbox but stay on an open detail page; failed or interrupted applications stay visible with a reason to review the host's policy. They are not retried automatically.

Pending and failed requests also offer a full-width, neutral outlined **Close request** below the decision buttons, including when Approve is disabled. Closing removes the request from the inbox without approving or denying its scope. It does not change policy, restart or resume the agent, retry the action, or undo policy work left by a failed application; the latter still needs host review. It does not settle a native runtime approval. The same host-person authority applies. Host behaviour is [enclos ADR 0054](https://github.com/victorbonnet/enclos/blob/codex/mobile-close-policy-requests/docs/adr/0054-closing-a-policy-request-is-not-a-denial.md), proposed in [enclos#227](https://github.com/victorbonnet/enclos/pull/227), a draft not merged: enclos's `main` has no `approval.close` message, protocol text or ADR 0054, so no bridge advertises the capability below and Close stays disabled on every host until that change lands.

Close needs a connected host, completed fresh sync and `approval.close` in that connection's `authenticated.capabilities`; absence means a host that cannot close requests (none can yet, above), with a disabled action that says so after sync. Offline or syncing controls explain that a fresh connection is needed. While submitting, all controls stay disabled and Close says **Closing request…**. The app sends `approval.close` with the stored request id and keeps the request visible until the host reports `closed`; an acknowledgment alone does not confirm closure. That receipt returns the submitting detail page to the inbox. Errors or disconnect leave it visible, with the host's message: a host refuses to close a failed request while its sandbox has a pending policy change, naming the host commands that settle it. An already-open detail page closed from another device says **Closed · no new decision** in neutral styling, without controls. Applying requests cannot be closed; whichever host operation wins the atomic race determines the outcome. Approval and denial outcomes remain unchanged.

Requests are kept in the app's private preferences, covered by its existing no-backup rules. On authentication the host's cached requests are replaced by its fresh sync; forgetting that host or clearing the cache removes them. They show offline with all controls disabled. Closure belongs to the host, so reconnect, another paired device, bridge restart and cache clearing preserve it; the same scope under the same active policy stays closed even when requested again. A delayed nonterminal update for an already-closed request id cannot reopen it. A later policy snapshot may produce a new request with a different id. Android is built; iOS follows the same behaviour and receipt contract when implemented.

Connections attributed to a host policy-test run stay blocked and logged but never become inbox requests, including private-IP probes. The proxy verifies a host-registered, sandbox-scoped marker; arbitrary client markers cannot hide normal traffic. A genuine agent request to the same address remains visible. The built-in network probe's reserved `probe.enclos.invalid` destination is not an approval request. The host suppresses new notifications for that exact host and retires existing pending ones as diagnostics without changing policy. Such notifications leave the inbox; a detail page already open says **Diagnostic probe · no approval needed** and offers no decision controls. Real destinations, including private addresses, remain eligible for requests.

### Groups

A group is one conversation between the person and two to six agents of **one sandbox**, which the host's bridge keeps and whose turns it runs (enclos ADR 0045, proposed; `docs/protocol.md`, Groups): the app shows it and sends the person's messages.

- **Starting one**: the compose button's agent chip lists **New group** when a sandbox has at least two agents. Its agents are ticked (once one is, only the agents of its sandbox can be), with a name or none (their names then); the first message starts the group (`group.new`, then the message). A group the bridge refuses (an `error` naming the `group.new`: a member it no longer knows, an older bridge) leaves the phone at once, and where it was started, or opened, says `The group was not started:` and the bridge's words.
- **In the conversations view**: a **Groups** section above the agents, each group with its members' avatars overlapping, its name, its last message with who said it, how long ago or the working wave, and its unread count. Groups are not in an agent's tree.
- **In the group**: the members' avatars and handles in the bar; each agent message with its speaker's avatar and name above it. Typing `@` lists the members matching what follows, with their avatars, and **@all** last ("everyone answers"); picking one puts `@handle ` in the field. `@handle` addresses that member, several those members, `@all` every member, each of whom must answer; a message naming no one invites them all, and they may pass.
- **Where it is**: a line over the field, from the bridge's `group.state`: `@coder is answering · round 1 of 3` with the wave and **Stop** (`group.stop`, which cancels queued turns and asks the runtime to interrupt the running turn. If the channel cannot interrupt it, the status says the run continues and its reply will be dropped. Earlier messages stay), then Settled, Paused after the rounds or the replies allowed, Stopped, or Failed with why.

### Names

A conversation has a name: its agent's, from what was said in it (Hermes names each session; the plugin passes the model's summary on, not the first message's cut), or the person's. Tapping the name in a conversation's bar renames it; the person's name replaces the agent's, which no longer replaces it, and clearing it lets the agent name it again. The bridge keeps the name and sends it to every device of the person (enclos `docs/protocol.md`, A conversation's name), so a name is saved only while its host is connected: until then the rename dialog says so and cannot save. A name is shown without the characters that change how text reads unseen (bidirectional overrides, zero-width characters: the app's `Visible` rule), whoever gave it.

### Agents

**Total and Working only.** At the top of Agents, outside the host groups, `0 agents`, `1 agent` or `N agents` is the total of distinct agents this phone lists for its paired hosts, including cached agents while a host is offline. An agent is its host and its `sandbox/agent`, not its display name: the same name on two hosts or sandboxes is two agents. Search, Working only and folded hosts leave the total as it is; conversations of an agent no longer listed, tasks, empty sandboxes and headings add nothing. The rows come from the same distinct roster. It is what this phone lists, not a live inventory of every host.

A labelled **Working only** switch, off when the app starts, shows only the agents the app shows at work, by the same decision as their row (below): conversation work (a message awaiting its answer, typing, a tool not ended, an answering report) or recognized runtime activity. A task record alone, usage, a capability, the connection or a recent message is no sign of work; absent or unknown-only activity with no conversation work leaves an agent out, which is not a claim that it is idle. It follows the roster, activity and conversation state as they change, with no polling, timer or loading barrier: a connection ending, or opened again over a live one (Reconnect, or Clear cache while connected), clears its host's work (typing, a message awaiting its answer, a tool not ended, runtime activity), leaving another host's work and what the new connection says after; a new agents list clears runtime activity until the next reports.

While on, a quiet line below the switch, outside the host groups, says **Shows work reported to this app. Offline or unreported work may not appear.** The total, the switch and that line are the list's first item and scroll with it. The total and the switch share a line where they fit, measured at the current text size; otherwise the switch goes on its own full-width line, never cut. The label and the switch are one control, at least 48 dp high, with the switch role, its name and its on/off state; the total reads as a total (`4 agents total`), not a control.

The search intersects Working only: neither changes the other. While on, only hosts and sandboxes with a matching agent at work show, without Create sandbox or empty sandboxes; a sandbox found by the search alone shows only while Working only is off. Host details, sandbox headings and the conversations-left-out notice stay for the hosts shown. A search or Working only unfolds the hosts it shows and turns their folding off without changing what was folded; with both off, the folds come back. With no match, Working only says **No agents working**, or **No working agents match your search** with a query, and offers **Show all agents**, which turns only Working only off (the search stays, so the view may still be empty) and puts focus back on the switch. With no host paired, the view shows `0 agents` and how to pair one, without the switch.

The choice lives in the app's model while the app runs: through the Inbox and Agents switch, an agent's or a sandbox's page and back, the lock, the background and a configuration change. It is not written to the phone, so a new process starts with it off. Clear cache keeps it; forgetting the last host hides it until a host is paired again. It applies to Agents alone: the Inbox's filters, a sandbox's page and the new conversation's agent chooser are unchanged, and the search text stays shared between the views.

**By host, then sandbox.** Each paired host has a heading, even when it is the only one: its connection (a filled square in `accent` while connected, an outlined one otherwise) and its name, with the chevron of the conversations view's sections, folding the host's sandboxes and agents away or back; what is folded stays so across starts, and a search shows only the hosts with something found, unfolded. A host with no agent yet says the host lists them once connected. Under it, each sandbox's heading (the Enclos mark, its name, its runtime), then its agents. No heading has a line under it.

**Empty sandboxes and creation.** A bridge that offers sandbox management to this device lists its sandboxes independently of their agents, including those with no runtime. They show `No runtime installed` until installation succeeds, and search finds their address and runtime as it does an agent's. The sandbox list is kept while the app runs; the runtime catalog belongs to the current connection. Both refresh on connection and after an operation; older bridges still show the sandboxes their agents imply. Each connected host offering management has **Create sandbox** under its heading, outside a search. The bridge offers this only to paired devices of the host's person ([enclos protocol, Sandbox creation and runtime installation](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#sandbox-creation-and-runtime-installation)).

Creation opens a full screen for that host: a name (2–41 ASCII characters, starting with a lowercase letter, followed by lowercase letters, digits or hyphens), and a starting policy, **Minimal** (only listed destinations and the runtime's hosts) or **Assistant** (the public web). Minimal is selected initially. Create stays off for an invalid or already listed name, while creation is pending, or without a management connection. The host checks the name, template and permissions again. Its progress and failures show on the screen; success opens the new sandbox's page. The phone chooses no backend: the bridge uses the host's supported backend.

**A sandbox's page.** Each sandbox heading in the agents view ends with a chevron, and tapping it opens the sandbox's page: its mark (in `accent` while its host is connected), its name, runtime and host; its agents as the agents view shows them, each opening its page (back from which returns to the sandbox's page); its groups, each opening; what it runs on (runtime and its version, its latest release when the host can tell whether it is newer, host, connection and the state when the bridge lists it); a Policy row with accepted-access count and active version, opening the policy page below; and a line saying its sessions show on the host (`enclos sandbox show <sandbox>`).

**Runtime versions (Android built; iOS not started).** A bridge that lists its sandboxes to the host's person sends, with each sandbox that has a runtime and when it knows them, the version installed and the runtime's latest release, the one its installer installs by default, with whether the host's enclos was checked with it and whether it is newer than the version installed ([enclos ADR 0074](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0074-a-sandboxs-runtime-is-updated-on-request-and-restarts-at-once.md), proposed; [protocol](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#sandbox-creation-and-runtime-installation)). The sandbox's heading in the agents view and its page name the runtime with its version (`Hermes 0.23.1`), the runtime alone when the host does not know it; when the latest release is newer, the heading adds `update available` and the page's Runs on has a Latest row saying so (`0.23.2 available · checked with this host's enclos`, or `not checked with this host's enclos yet`) and a line that updating the runtime from the app comes later; when the host says it is not newer, the Latest row says `0.23.2 · up to date`. When the host cannot tell whether the release is newer, such as when it does not know the version installed, nothing is offered or said of it. The bridge answers with the releases it has kept, however old, and, when a lookup is due, sends a fresh list once it has looked them up, which replaces the shown one; older bridges send none of these fields, and the sandbox reads as before.

**Installing a runtime.** A sandbox with no runtime offers the runtimes its connected host lists, with each one's name and description. Hosts offer OpenClaw once they support its app channel. Selecting one and tapping **Install <runtime>** asks that host to run the runtime's own installer inside this sandbox, under its policy, as the host CLI does. The screen says installation can take several minutes and that login and channel setup continue on the host. While pending, installation cannot be submitted again; progress and the host's failure message show in place. Success updates the runtime and shows the host's remaining setup command, selectable to copy. Installing a runtime does not mean an agent is ready for chat: the runtime's login, app channel configuration and service startup still happen on the host. After completing setup, restart the bridge to list the new agent. A sandbox with no agent says so.

**Connection changes during an operation.** Creation and installation are never queued or retried automatically. If the connection ends before the host confirms the outcome, the screen stops showing progress and says to reconnect and check the sandbox before trying again. An installation already running on the host continues; on reconnect the app refreshes the sandbox list. Responses are matched to the request and host that started them. A terminal reply for that request naming a different sandbox, runtime or operation ends progress with a failure and asks the person to check on the host. Hosts that do not offer management keep their existing read and chat behavior.

**An agent's row**: its avatar (pulsing while it works), its name, and, while it works, the wave and what it does (the tool it runs, as its label says, else `working`), else when it last sent a message (`active 3 hours ago`, `active yesterday`, its runtime's notices aside), `no message yet` before its first one; from a host with `usage`, what it used over the last 24 hours, faint at its end (`1.2M tokens · 24h`, its calls for a runtime that counts no token, nothing when it made no call), so an agent using a lot stands out ([its day](#an-agents-page)); a chevron at its end, and tapping it opens [its page](#an-agents-page). An agent works on a conversation from the person's message until its answer, while its runtime says it is writing, while a tool it started has not ended, and while its runtime reports it answering there; it also shows at work, with what it is doing in place of the tool (`working on a task`), while its runtime reports any [activity](#agent-activity-and-tasks). The phone knows only what comes over the bridge, so not, for instance, a routine its runtime does not report as activity (Hermes reports none yet).

The search finds agents by their address and runtime. With no host paired, the view says how to pair one. A person sees only what is shared with them; the list never hints that more exists.

### An agent's page

Opened from an agent's row, its menu's About, or a sandbox's page. If the host stops listing the agent while this page is open, it says so and offers [Forget](#forgetting-a-removed-agent) once the host confirms removal. Its avatar (pulsing while it works), name and address, and, while its runtime reports it at work, the wave and what it is doing; **Conversations**: its [Home](#home) ("Cron jobs and the agent's notices come here."), which opens, **New conversation** with it, and how many other conversations it has, in the conversations view; **Runs on**: its runtime, sandbox, host and the host's connection, and what its channel lets it do once the bridge has reached its plugin (says when it is working, shows the tools it runs, names conversations, lists its commands, sends files, says what it is doing, reports its tasks, shares its tasks' details), else that this is known once its host reaches it; **Usage · last 24 hours**, from a host with `usage`: its tokens in all and the line of [a host's usage](#a-hosts-page) (`26 calls · 845.8k in (90% cached) · 6.1k out`), and what is counted: the person's conversations in the app, or, for the host's person, all its calls when its plugin reports those outside the app, else `In the app only`; or why there is none (not connected, an older host, still loading, the host's error, or an agent past the 190 a report lists); **Tasks**, for an agent whose runtime reports them (below); **Commands**, when its runtime lists them, the first six with **Show all**. Read only: changing an agent from the app comes later, for the host's own user, which the page says.

### Agent activity and tasks

What an agent does outside a conversation's answer is its runtime's to report, through two optional capabilities of the protocol (enclos [`docs/protocol.md`, Tasks and agent activity](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#tasks-and-agent-activity); [enclos ADR 0068](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0068-tasks-and-agent-activity-are-reported-not-controlled.md), proposed). Both are reported, never controls: the app cancels, retries or unblocks nothing.

**Agent activity** says what an agent is doing now: answering in a conversation, running a routine, working on a task, several at once, or nothing. The bridge sends it after the agents' list for each agent not idle, and whenever it changes; an empty list is idle. While an agent is not idle, its avatar pulses and the wave shows, with what it is doing, in the conversations view, the agents view, its page and the bar of a conversation with it alone (in place of its address there): `working on a task` when one of its entries is a task, else `answering`, else `running a routine`. On its page and in the bar of a conversation with it, `working on a task` opens that task's [sheet](#a-tasks-sheet) when the phone keeps the task. Its `answering` entries show that conversation at work too, as a person's message does. Activity is live state: it is not kept on the phone, a new agents' list replaces it, and it is cleared for a host when its connection ends, is replaced, or the host is forgotten, so an indicator never stays on for a host the phone no longer hears.

**Tasks** are work an agent does outside a conversation's answer, which its runtime tracks until it ends (a task another agent put on Hermes's board for it). They show only for an agent whose capabilities in the agents' list include `tasks`, and the bridge sends them to the host's person only. Each task is known by its host, its assignee's sandbox and the runtime's id. The bridge sends every task it keeps at each sync and each change as it happens, and says when it stops keeping one; the phone keeps them with the host's other data, so they show before any connection, and once a sync ends it drops the tasks of that host the sync did not send. Forget this host and Clear cache remove them.

- **The asking conversation.** A task asked for in a conversation is a card in it ([ADR 0010](adr/0010-a-task-card-sits-in-its-conversation-without-being-a-message.md), proposed): a framed line, not a bubble, with a mark (a pulsing square while it runs, an outlined one while queued or blocked, a check once done, a cross once failed or cancelled), its assignee by its shown name, its title and where it is, `Engineer · Fix the login page · running 12 min`, the time counting up while the conversation is open. Once ended it says `done`, `failed` or `cancelled` and shows its summary under the line. It updates in place, and tapping it opens the task's [sheet](#a-tasks-sheet). It sits after the last message at or before the `since` the task first came with (when it entered the state it was in then), and stays there as the task moves on, moving earlier only if a later report gives an earlier `since`; a task first seen after a cleared cache is placed by the state it is in then. It is not a message: it is never unread, never previews in the inbox, is not searched, and leaves when the bridge stops keeping the task.
- **Task lines.** A task event is a change of a task that its runtime announces to a conversation, such as Hermes's kanban ping when a task is done, blocked or sent to triage (enclos [`docs/protocol.md`, Task events](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#task-events); [enclos ADR 0071](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0071-a-runtimes-task-events-reach-the-app-as-task-lines.md), proposed). It is not the agent talking, so it shows as a **task line**, never a bubble ([ADR 0013](adr/0013-a-task-line-is-quiet-history.md), proposed): a quiet centred line, small and faint, with its time, as a status line is: the task's id and title, its assignee by its shown name, and what happened (`blocked`, `gave up`, `crashed`, `timed out`, `done`, `ready for review`, `changes requested`, `sent to triage`, or `changed` for any other change and for an event the app does not know), then `→` and where the task is now when the runtime says and the event does not already: not after the same word (`done`, `blocked`), never after `ready for review` (Hermes's review status reads as `blocked`), nor after `sent to triage` while `queued` (`t_a09759c7 S2a · Reviewer · sent to triage · 14:02`, `t_3f9a12bc Fix login · Engineer · changed → running · 14:05`). The id and title give way first when the line is too long; the rest keeps its room and is cut short only when it alone does not fit, as a long shown name on a narrow phone can. The app announces `task_events` in each connection's `auth`; a bridge sends the event's details only to a device that does, and to any other the runtime's own text as a `notify`, as before. A task line is a message of the conversation's history, kept on the phone with its details and brought by each sync like any other, but quiet: it is never unread, never pushed (the bridge pushes none), carries no suggested reply, the inbox previews the last other message when there is one, and it does not count as the agent last active; search finds it by its line's words (its assignee by handle), not by the runtime's text. A message of `kind: task_event` whose details the app cannot read (no task id, or one with a hidden character, no title, no event) is its text as a `notify`, live and from the cache; an event or a state the app does not know reads as `changed` and as none; the title is cleaned as a task's (one line, no hidden character, 120 characters) and an assignee that is not `sandbox/agent` is left out. **Open task** under the line opens the task's [sheet](#a-tasks-sheet), which asks `task.get` with the event's assignee and task. It is offered only when the phone keeps that task from the bridge's tasks (same host, sandbox, id and assignee). The bridge sends tasks to the host's person only, and answers `task.get` from anyone else `not_allowed` and for a task it does not keep `not_found`; a phone that keeps the task is the host's person's, so only they see Open task. A phone that does not keep the task, the host's person's before a sync brings it included, offers none, even when the bridge keeps it. The line has no other action. A task line that carries files shows them under it. The agent's answer to the event, in the turn its runtime wakes it for, is its message as before.
- **The agent's page.** A **Tasks** section lists the agent's tasks: those still going (queued, running, blocked) first, then those that ended, each the most recently changed first, five ended ones before **Show all**. Each shows its mark, its title, where it is with who asked for it (`running 12 min · asked by Lead`), and its summary once ended; each opens the task's [sheet](#a-tasks-sheet). With none, the section says so, and that only the host's person sees an agent's tasks.
- **Untrusted text.** A task's title, summary and names come from the sandbox. The bridge cleans them; the app cleans the title and summary again (one line, no hidden character, the title cut to 120 characters, the summary to 500), checks the names as ids (`sandbox/agent`, at most 128 bytes, no control character), and draws them as plain text, never markdown or links, the title on one line. A task the app cannot read (a state it does not know, a blank title, an assignee that is not `sandbox/agent`) is answered `bad_message` and skipped. A task may also carry how many comments it has (`comments`), which the phone keeps with it.

#### A task's sheet

Tapping a task, wherever it shows (a row of the agent's page, a card in a conversation, `working on a task`, a task line's **Open task**), opens its sheet over the screen; it no longer opens the conversation. It is read only, as tasks are (enclos#318, step 1, within ADR 0068): no edit, no comment.

- **What the phone keeps**, first: the title in full, the mark and where it is (`running 12 min`), `Assigned to` and `Asked by` with the agents' shown names, and the summary once ended. Then **Open the conversation it was asked in**, when the phone holds that conversation: it closes the sheet and opens it.
- **What the runtime holds**, fetched when the sheet opens: the app sends `task.get` with the task's assignee and id, and the bridge answers `task.detail` from the assignee's plugin (enclos `docs/protocol.md`, Task details; enclos #319). It is asked for only while the host is connected and the agent's capabilities include `task_details`; otherwise the sheet shows what the phone keeps and says why there is no more: "Details need the host connected." or "This agent's runtime doesn't share task details." While it comes, "Loading details…". It is kept in memory for the open sheet only, never on the phone, and goes when the sheet closes, another task's sheet replaces it, or the host's connection ends (it is asked again once the host is back). It is asked again when a `task` for the open task changes its state or its comment count; a change while a request waits asks again once that one is answered, whether by the detail, an error or no answer in time. A request that fails with no such change is asked again only by the person's Retry.
- **Body**: what the task asks, in full, drawn as [markdown](#5-messages) as an agent's message is, selectable to copy. Its links open as a message's do: a bare link at once, one whose text is not its own address after a confirmation naming "this task".
- **Related work**: the tasks it waits for (parents, ↑) and those that wait for it (children, ↓), each with its title, mark and state when the runtime gives one, and its assignee's shown name. One the phone keeps (same host and sandbox, same id) opens its own sheet in place; another does not open.
- **Comments**, `Comments · 5` with the total: the newest the bridge carries (20 at most), oldest first, preceded by "3 earlier comments not shown" when the total is larger. Each shows its author, how long ago (`5 min ago`) and its full text, drawn as markdown and selectable as the body is, so at the body's size rather than the smaller one of its author line. An author the plugin names as an agent the host serves (`agent`, `sandbox/agent`) shows by that agent's shown name and photo; any other author shows as the runtime's own name for it, in mono and muted, so it does not read as an agent of the app. With none, "No comments."
- **History**: what happened to the task, oldest first: `Created by Lead`, `Attempt by Engineer · crashed after 1 min` (an attempt that ended: its outcome, `completed`, `blocked`, `crashed`, `timed out`, `gave up`, `failed`, `stopped`, or `ended` for one the app does not know, and how long it took), `Attempt by Engineer · going for 3 min` (one still going), `Blocked`, `Unblocked`, `Review asked for`, `Done`, each with how long ago, and its line of text under it (an attempt's summary or error, why it blocked). A kind the app does not know is left out.
- **Errors.** An `error` answering the request shows its message as plain text, with **Retry**: `not_allowed` (only the host's person), `unknown_agent`, `not_found` (the runtime no longer keeps the task, or it is not that agent's), `unsupported`, `agent_unavailable`, `unconfirmed` and `unknown` (the plugin did not answer), `internal`; a blank message reads "The host could not get this task's details." No answer within 30 seconds says "The host did not reply. Try again."; a request that could not be sent says so. Nothing is resent on its own; a late answer to a request whose wait ran out still shows.
- **Untrusted text.** Every text of the detail comes from the sandbox. The app reads it leniently (a part missing is empty, an entry it cannot read is left out) and cleans it again to the bridge's bounds: the body (4,000 characters) and each comment (1,000) without hidden characters and with their lines kept, blank lines in a row made one (enclos-protocol's `paragraphs`); titles (120), authors (64) and history lines (300) on one line; names checked as `sandbox/agent`; at most 20 related tasks, the newest 20 comments and 30 history entries. The body and comments are markdown, drawn as a message's ([ADR 0002](adr/0002-messages-are-markdown-drawn-by-the-app.md)): nothing in them is fetched or run. Everything else is drawn as plain text, never markdown or links.

### New conversation

The compose button's screen: Close; the agent it is with, a chip at the top (its avatar and name, the agent most recently active first), whose list picks another agent or starts a [group](#groups); the agent's card in the middle (avatar, name, sandbox, runtime and host, and how many commands it has); and the field. Opened to ask an agent why a policy request was needed, it starts with that agent and the question in the field (see [Sandbox policy requests](#sandbox-policy-requests)). The first message starts the conversation (a draft until then, which the bridge learns of with that message, `conversation.new` then the message, so a screen left before sending leaves nothing behind) and opens it. A send that does not go leaves the person on the screen with the text and why it did not go, and the next tap reuses what the last one made: the same draft while the agent is the same (another agent's draft is dropped), the same group while its members and name are the same, so a failed send makes no second group on the host. Sending needs the agent's host connected, as in a conversation. A conversation screen whose conversation the phone does not hold (a draft whose saved owner was lost, or one forgotten or cleared while open) goes back to the first screen.

### Routines

The list and editor use the same visual controls as the rest of the app: hairline-separated rows, outlined schedule choices, 12 dp form controls, the shared primary button and the app-lock switch colours. Addresses and run metadata use the existing monospace styles; confirmations reuse the app's shared dialog. Light and dark themes use only the app palette, including selected and disabled controls.

An agent advertising `routines` offers **Routines** from its actions and agent page to the person its host lets manage them (`can_manage_routines` in the agent list: the host's person only, and no one on an older host that does not say); a person the agent is only shared with sees no Routines entry. The page is scoped to that agent on its host, with a back action, refresh and a **Nothing scheduled** empty state. It lists enabled, paused and completed routines with schedule, next run and last observed result; selecting one loads the current definition when that control is available. The runtime may report an explicit set of available operations (`get`, `create`, `update`, `delete`, `set_enabled`, `run`). Unavailable operations are hidden or disabled and cannot be submitted by the app model. A read-only runtime exposes no New action, including in the empty state. Missing operation metadata preserves the preceding runtime behavior; unknown operation names enable nothing. The runtime owns definitions and execution ([ADR 0007](adr/0007-routines-are-runtime-owned-controls.md), proposed), so the app must refresh to see changes made by its own tools or another device. Lists are paged and never download every routine's full prompt at once.

The create/edit flow has an optional name, instructions, schedule and **Send to**. Daily starts at 09:00; Weekly chooses weekdays and a time; Monthly chooses a day and time; Repeat chooses a positive interval; Once chooses a date and time; Custom accepts a cron expression. The editor preserves a custom expression when it cannot be represented by a preset. Scheduling uses the runtime's reported timezone, shown in the editor, including when it differs from the phone. Next/last-run times are observed runtime values, not local predictions. **Nowhere** saves the result only; authorized direct conversations and Home with this agent can receive it, including archived direct conversations and a Home archived by an older version. Routines with existing external destinations, a secondary failure destination, a custom endpoint, monitors, chained context or session attachment are shown read-only, preserving their native settings.

Advanced settings are offered only when supported: skills loaded before the instructions, a model/provider override or runtime default, default toolsets versus an explicit selection, script-only execution, a relative script path and an absolute working directory. Catalog suggestions keep model/provider pairs together; explicit model, skill and toolset IDs allow values outside the bounded suggestion list. A refreshed runtime timezone differing from the editor’s initial zone requires reopening before saving. Default toolsets and an empty selection are distinct. Script-only requires a script and delivers its output without a model; a script is a file in the agent's scripts directory, never a command line. Working directory and script settings grant no additional sandbox access. Unknown existing native settings survive edits.

The page supports editing, explicit pause/resume, running now (an enabled routine only: a paused one is resumed first; confirmed first, naming the routine and where its output goes) and confirmed deletion. Deletion removes the runtime definition and may remove its saved output; it does not promise to stop an already-running execution. Controls wait for correlated replies and show failures beside the affected flow. Definition revisions prevent an old editor replacing another edit; a conflict requires reloading. Offline controls are disabled with a connection explanation. A timeout or disconnect after dispatch can mean the outcome is unknown: refresh before deciding whether to try again. Mutations are neither queued offline nor automatically resent. Management initially requires the host's person; the bridge enforces this and validates delivery choices, independently of the app. A routine that changed since the person chose it (a refresh brought a new revision) is not acted on, and the page says so.

What the runtime writes is shown as its text, never as the app's: names, previews, delivery and choice labels, states, pause reasons, last results and errors and the time zone are drawn without the control, bidirectional and invisible characters that would change how they read (the same rule as enclos-protocol's `visible` module; joiners between non-ASCII characters are text), and a refusal from the host is quoted as the host's reply. The definition, which goes back to the runtime, is kept as it came: when its name or instructions hold such characters, the editor says so and saves them unchanged.

### An agent's model

**Android built; iOS not started.** An agent whose channel advertises `model`, listed with `can_manage_model` (the host's person only), has a **Model** section on its page, showing the model and its model provider once read, that opens the agent's **Model** page; another person sees neither, nor the capability among what the agent can do. The runtime keeps the setting and its catalogue ([enclos ADR 0069](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0069-an-agents-model-is-changed-through-its-runtimes-channel.md), proposed; [enclos `docs/protocol.md`, An agent's model](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#an-agents-model)); the phone keeps nothing across app restarts. The choice is the agent's own, for all its conversations; a model a conversation sets with the runtime's `/model` command still wins there.

The page reads the agent's model on opening and on Refresh: **Now:** with the model and its model provider, then the model providers the runtime lists, one per row. A model provider the agent cannot use yet is shown disabled, with what the runtime says to do on the host; it cannot be chosen, and no secret is ever entered on the phone. The agent's own model provider starts picked when the runtime lists it as usable. When it does not, the page says why and asks to choose one: the runtime does not list it (Hermes's `auto`, say), it cannot be used yet, or the settings name none. A picked model provider the runtime no longer lists as usable is unpicked. Picking a model provider loads its models, each row its label with its id under it when they differ, the picked one marked, else the current one; one offering more than the runtime lists says so. Models are loaded again after a refresh, once nothing else is pending, and once the host is back. A load that failed says why, and offers to try again unless asking again would fail the same way (a list too large to show); it leaves the options fresh, so a typed model ID can still be saved. A failed load of one model provider's models does not stop another's. When the runtime takes ids it does not list, **Another model ID** accepts one. Picking a model or typing one sends nothing. **Save**, in the top bar beside **Refresh** so it stays in reach whatever the list's length, sends it, and until then the page names the choice under **Now:** as not saved. A runtime that restarts to apply it says so there too. **Save** is enabled only for a usable model provider and a model other than the current one, on fresh options, with no request pending; once a save is confirmed, what was picked or typed is cleared, the saved model being the current one. What was picked or typed is kept through a rotation and the app lock.

A runtime that applies a change on the agent's next turn saves at once and says so (`Saved. … answers from the agent's next message.`). One that applies it only once its service restarts says, before saving, that every agent the service serves restarts, and asks to confirm; the question goes away if the save can no longer be sent, and a save that could not be sent says so. A change made since the page was read (another phone, or on the host) is refused by the runtime: the page says so and must be refreshed before saving again. A save the runtime refuses for its model provider or model changed nothing, and the page keeps its options. Requests are never queued or resent. A save whose answer times out, whose connection drops, or that the host reports as not confirmed leaves its outcome unknown and the options stale: the page says the model may have changed and to refresh before trying again. A model list that times out changes nothing else. A notice of a confirmed save is dropped when the page asks the host again. With the host connected but the agent's channel not offering `model`, the page says the runtime does not offer it right now rather than asking to connect. The page uses the app's rows, sections, check glyph, form field, action button and shared dialog, in both themes; its rows read as a choice to screen readers.

iOS will offer the same section, page and rules natively (see Platforms).

### Agent display names

The agent page offers **Rename** for its shared display name, using the same field and actions as the app's other editors. The host stores this name and supplies it to every connected app that can see the agent ([enclos ADR 0051](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0051-agent-display-names-belong-to-the-bridge.md), proposed). This is shared agent presentation metadata, rather than a private phone preference. Only the host's person on a still-paired device may change it.

For example, `comptoir-dev` can appear as **Gégé Commit**. Display names support Unicode and spaces, are trimmed, and must contain 1–100 Unicode code points using at most 400 UTF-8 bytes, without controls, line separators or characters that change how text reads without showing (bidirectional overrides and isolates, zero-width and other default-ignorable characters, the soft hyphen, tag characters, variation selectors and blank fillers: the same rule as enclos-protocol's `visible` module), so a name cannot read as another agent's. The zero-width joiner and non-joiner and the emoji variation selectors are part of a name only between two non-ASCII characters, as in a joined emoji or Persian spelling; next to ASCII, at an end or beside another such character they are refused. The editor refuses such a name; a listed name holding one is not shown, and the handle stands in for it. The host also refuses a name that reads as another listed agent's handle. Two names that differ only by joiners read alike: a mention suggestion shows a display name beside its `@handle` only when it reads differently. **Use original name** explicitly clears the display name. The stable address stays visible on the agent page; addresses, conversation identity, runtime configuration and `@handles` do not change. The agent's own memory, prompt and native channel name stay as they were.

Lists, agent pages, unnamed conversation headers, group member/speaker labels, avatar initials and accessibility labels use the current shared display name, falling back to the stable handle when no name is set. Older messages' agent labels resolve the same current name; message records and conversation titles are not rewritten. Search finds both display name and stable address/handle. Mention suggestions show the display name with the handle and still insert the stable `@handle`. Duplicate display names are allowed, so addresses/handles remain available to distinguish agents.

The editor fetches current metadata before editing, retains its opening revision and waits for a correlated host confirmation. Nothing is renamed optimistically or queued offline. A stale edit requires reloading/reopening; the new host metadata does not silently replace a draft or count as its successful save. Disconnect or a missing confirmation requires refreshing before retrying. The phone keeps the highest name revision it saw for each agent address; after a bridge's database is reset or restored from an older copy, it keeps its older name until the person clears the cache. Offline, non-owner and unsupported-host states explain why editing is unavailable; an older host says to update the host. This change does not deploy or restart a bridge.

Android caches the display name and its nonnegative revision in the agent row, scoped by host and canonical agent identifier. The additive cache upgrade retains existing agents and conversations, with revision 0 and no display name for older rows. Lists, broadcasts and background cache reads preserve the newest observed name revision. Clear cache and Forget this host remove only the phone's copy, and reconnect restores the host's value. Android implements this first; iOS follows the same behaviour when built.

### Agent photos

Tapping the avatar on the agent page opens the photo picker. When a photo is set, **Remove photo** appears below it. There is no separate Change photo button. A photo belongs to the agent on its host and is shared across apps connected to that host. The host owner can edit it while connected to a supporting host; other paired people can see it. The platform's photo picker grants access only to the selected photo. Cancel leaves it unchanged. The app prepares a small square photo, then waits for host confirmation; progress and failures appear by the controls. Remove asks for confirmation and restores the coloured initial everywhere. An older host keeps the initial and disables changing the photo.

The same round photo appears in agent and inbox rows, agent pages, conversation headers, group stacks and speakers, mentions and identified sandbox requests. Working indicators remain visible. With no custom photo, existing initials remain; with one or without, the agent row's corners still say whether its host is connected. Photos are keyed by the host and the agent kept apart (never one joined string, since a host's name may hold `/`), so equal agent names on different sandboxes or hosts do not share an image. The app takes a photo only for an agent its host lists, drops it when the host no longer lists the agent, and keeps at most 64 photos per host. The host's agent list is its word on each photo, even at a lower revision than the phone last saw (the host's database may have been made again); between lists, older revisions are ignored. When the host confirms a photo this phone just set but the phone does not take it (past its 64, or the agent no longer listed), the photo controls say why instead of going quiet. A photo message without its agent or revision is ignored.

The host stores and versions the asset ([enclos protocol](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#shared-agent-photos)). Connected apps receive changes and removals, and reconnect fetches the current version. A stale edit is refused and refreshed so it cannot overwrite another device's change. Cached photos survive app starts for offline display, with editing disabled offline. Clear cache and Forget this host remove only the phone's copies; the shared host photo remains. Android is built; iOS follows when implemented.

### Sandbox policy management

The sandbox page's **Policy** row opens its active policy. Entries are grouped into collapsible sections for allowed destinations, private network access, writable paths, protected read paths, network mode and incoming connections, resource limits, network logging and secret references. Active entries that came from approvals say **Accepted access**; inherited and sandbox-specific settings name their origin. The active policy is the source, so removed entries stop appearing even though an approval remains in history. All accepted entries remain discoverable regardless of the inbox history window.

The host's person can add, edit or remove an access entry and change default settings for **this sandbox only**. Tapping an editable entry opens a small editor; **Remove** requests a removal. Values and the host's change lines are shown with their hidden characters written out (⟨U+202E⟩), and a typed value holding one is refused before any preview, so the review reads as what the host saves. **Review change** asks the host for exact effects, followed by **Save policy** or **Save & restart**, which asks for the phone's biometric or screen lock first (the [app lock](#app-lock)'s prompt: a strong biometric or the screen lock), every time and whatever the app-lock setting; cancelled or failed, nothing is sent and the review says what the system said. A phone without a screen lock cannot save a policy edit, and the review says to set one. The review explains when all running work ends and services restart. No change is optimistic or queued offline. The host refuses stale previews, pending or unapplied changes, invalid paths or destinations and protected built-in read-deny edits. Removing the last private destination also removes its unused private-address opt-in; public network mode's continuing web access is disclosed. Every agent receives updated active-policy knowledge after a save. Secret references and network logging are read-only; secret contents are never sent.

Cached policy is kept in the app's private preferences, under its no-backup rules, in plain text like the cached requests: it holds host paths, destinations and secret reference names, never secret contents. It is visible offline and survives app starts, but editing waits for a fresh host response on the current connection: a connection that ends or is replaced makes it stale again. Refresh asks again; another device's save updates this page and dismisses an obsolete review. Connection loss or a missing confirmation requires refreshing before trying again. Clear cache and Forget this host remove cached policy. Only a still-paired device of the host owner may load or change it; when the host answers that this person is not its own (an agent shared with them), the sandbox page drops its Policy row ([enclos ADR 0047](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0047-the-hosts-person-manages-sandbox-policy-from-the-phone.md), proposed). Android is built; iOS follows when implemented.

### A host's page

The **Host details →** row inside each unfolded host in Agents, and the host's name or chevron in Settings, open its page. The host heading's chevron only folds and unfolds its contents. Back returns to the place it was opened. The page shows the host's connection, address, Reconnect while offline, the sandboxes in its agent list, each opening its page, and [Forget actions](#forgetting-a-removed-agent) for agents the host confirms removed.

**Audit (Android built; iOS not started).** The host's person can read state-changing commands on this page when the bridge advertises `audit`. Opening the page or reconnecting while it is visible loads the newest entries first; Refresh replaces them with a fresh page, and Load older entries appends the next page. Each entry shows the command and target, date and time in the phone's locale, actor and host, result (Succeeded, Failed, or No outcome recorded), outcome message and completion time when recorded. No outcome recorded may mean a command is still running or never finished. Host display summaries may end in an ellipsis; the full audit stays on the host. Reading entries does not run the host's integrity verification.

**Usage (Android built; iOS not started).** When the bridge advertises `usage`, offered to every person, the page shows what each agent used in the person's own conversations on that host over the last 24 hours, 7 days or 30 days, chosen with three tabs (7 days at first). Each agent is a row: its name, its address under it (two sandboxes may have agents of one name), its tokens in all (`845.8k tokens`; its calls, for a runtime that counts no tokens), and one line: calls, what the model was sent with the share read from the cache, and output (`26 calls · 845.8k in (90% cached) · 6.1k out`); the agent that used the most first. The bridge sums from the start of the hour that holds the window's start, and counts only what reached it: calls in app conversations, not a talk in the sandbox or a routine's run, which `enclos usage` on the host reads from the runtime itself. Opening the page or reconnecting while it is visible loads the window, as does choosing another and Refresh. Loading, an empty window, failures, connection loss and an older host (no `usage`) are stated in place, as for the audit; a late answer to an earlier request is ignored. While another window loads, its tab is selected and the rows of the last one are hidden; if that request fails, the tab and rows of the last window come back. A report the app cannot read is said, not shown as no usage, and an agent listed twice shows once. Authenticating without `usage` drops the rows. The window's rows are held in memory, kept while offline (labelled saved in memory) and dropped when forgetting the host. The numbers are the runtime's, counted inside the sandbox: a guide to what an agent used, not a bill (enclos `docs/protocol.md`, Usage).

**Usage over time (Android built; iOS not started).** From a bridge that also advertises `usage.series`, the section shows above the rows when each agent used what: a stacked bar chart, a bar an hour for the last 24 hours and a bar a day for 7 or 30 days, days starting at the phone's midnight, each bar from the bucket that holds the window's start to the one that holds the time the report was asked, empty ones too. The bars are those of the report, drawn from when it was asked and the phone's offset from UTC then, however long the page stays open and wherever the phone goes; a day is named by its own date at that offset, a clock change inside the window included. Should a bucket of the host's fall on none of the bars, the section says how many, which the rows still count. Each bar stacks the agents that used the most (the bridge's 8, the heaviest at the base), each in its color, with a gap of the background between them, every agent of a bar visible however small its part; the scale's top and the first and last buckets are named faintly. Tapping a bar reads it above the chart (its time, its tokens, and each agent's), in text colors; tapping it again clears it. An agent keeps its color whatever the window and whoever else used more: its place among the host's agents, sorted, picks one of eight fixed hues (for the host's first eight; an agent the host no longer lists comes after them, and one past eight takes a color free in that chart) (the dataviz reference palette, light and dark steps checked against the app's backgrounds; three light hues are under 3:1 against the background, so every value is also given as text). The rows are the chart's legend and table: a charted agent's row starts with its color, and every row keeps that room, so the names line up. An agent whose runtime counts calls but no token has no bars and no color; its row says its calls. Series the app cannot read are said, as rows are, never drawn as no use; the chart is hidden when no token was counted. The host's person also sees the calls outside the app that each agent's plugin reports, its routines and its other chats beside the app's conversations (enclos `docs/protocol.md`, Usage); the section says so, and an agent whose plugin does not report them says "In the app only" under its row. A screen reader hears the window, the bucket that used the most and who led it; the rows give every value.

**Cost (Android built; iOS not started).** From a bridge that advertises `usage.cost` (enclos issue #343; enclos `docs/protocol.md`, Usage, Cost), what each agent and sandbox used comes with what the host estimates it cost, from the host's own price list. The app asks for costs (`cost` on `usage.get`) only of a host that gives them; an older host's report is unchanged. A runtime that counts calls but no token shows no cost, which no price list can tell. A subscription's tokens, which count against its limits, not in dollars, are priced at their model's list price as if paid (`included_usd_micros`), so a heavy agent on a subscription shows as heavy and its person can choose a lighter model. A cost reads as the host's CLI writes it: `~$1.24`; `~$12.40 (included)` when all of it is on a subscription; `~$13.64 (~$12.40 included)` when some is, or when paid tokens with no price sit beside it; `≥` before it when some tokens, paid or on a subscription, are of a model the host has no price for; `included` when every token was on a subscription with no list price; `?` when paid tokens had no price and nothing could be priced. An unknown cost is never shown as $0. On the host page, each agent's row gives its tokens beside its name and its estimated cost on a line under it (`Est. cost ~$1.24`), the name and address each on one line, cut with an ellipsis rather than wrapped, so a long cost never squeezes them; a By sandbox list above the agents gives each sandbox's tokens and cost the same way, every agent of it summed (the host's 20 that used the most); a sandbox's row opens its page. A sandbox's page (once it has a runtime) and an agent's page have a Cost and tokens section: the same three windows as the host page and Refresh, Cost or Tokens, the window's total (`~$3.40 · 1.2M tokens over the last 7 days`), and a bar chart of the sandbox's or agent's usage over the window, a bar an hour for 24 hours and a day for 7 or 30 days, built and named as the host page's chart, in dollars or in tokens, drawn from the report's sum of that sandbox or agent (`usage.get` with `sandbox`, and `agent` for an agent). A bar's dollars count a subscription's at list price and leave out what had no price; a bar read out says its cost as the rows do (`≥~$0.75`, `included`, `?`); the section says when some tokens had no price (the cost is at least the one shown, or unknown when nothing was priced) and when some were on a subscription, and that those are priced at list price only when some had one. Switching between Cost and Tokens only redraws; a window is asked for when the page opens, from its tabs, and again when the page is opened again. Loading, an empty window, failures, a host without `usage.cost` and connection loss are said in place, as on the host page; a late answer is ignored; a report the app cannot read is said. The answers are held in memory by sandbox and agent, dropped when the host stops advertising `usage.cost` or is forgotten. Every cost is the host's estimate, at its price list's base rates: a guide, not a bill; the model provider's own account is the record of what was billed.

**An agent's last day (Android built; iOS not started).** The agents view, a sandbox's page and an agent's page show what each agent used over the last 24 hours, from one `usage.get` per host without series: the same sums as the host page's 24 hours tab, so they count what that tab counts. They ask while one of them shows, again once the answer is two minutes old, never while a request is out, and keep the last answer when a request fails or times out (15 seconds) or the connection ends. An agent the report does not list made no call, unless the report lists 100 agents or more (the most it lists without series, by name, since reports carry costs; an older host lists up to 190) or has a row the app cannot read: then it is unknown and shows nothing. From a host with `usage.cost`, an agent's page also says its last day's estimated cost. The answers are held in memory only, dropped when the host stops advertising `usage` or is forgotten.

Loading, an empty log, failures with retry through Refresh, and connection loss are stated in place. Replies and errors must match the outstanding request for that host; late replies after a timeout or disconnect are ignored. Entries are held only in memory, cleared with the cache or when forgetting a host, and removed on authentication without the audit capability. Offline entries are labelled as saved in memory. Older bridges and connections as another person explain that audit viewing is unavailable; they receive no audit requests. The bridge rechecks host ownership and device pairing on each request (enclos `docs/protocol.md`, Host audit).

### Settings

In sections, each named small, faint and in capitals above a hairline, its rows separated by hairlines. Nothing here acts on a sandbox.

- **Hosts**: each paired host, its connection (who it is connected as, or why not), the bridge's last error, its address, then Reconnect (when it is not connected) and Forget this host on one line; and a last row, Pair a host, with the QR glyph.
- **Security**: the [app lock](#app-lock), a switch beside what it does; the whole row toggles it.
- **Appearance**: the [theme](#7-theme).
- **On this phone**: what is kept (and, when it could not be read, such as after going back to an older build, that it could not), and Clear cache.
- **About**: the app's version and the core's.

- **Forget this host**, after a confirmation: connected, the app asks the bridge to unpair this phone (enclos `docs/protocol.md`, `device.forget`); not connected, the host keeps it listed until `enclos app unpair` there, which the confirmation says; when the connection ended between the confirmation and Forget, the app says so after it. Either way the phone deletes its device key and Noise key for that host, and everything it kept from it: agents, conversations, messages, tasks, files (those of messages not read from the phone's copy yet too), how far they were read, whether its heading in the agents view was folded. Pairing again with a host deletes the device key of the pairing it replaces, and at each start the app deletes any device key no paired host uses. The conversations stay on the host. Using it again means pairing again.
- **Clear cache**, after a confirmation: deletes the conversations, messages, agents, tasks and files kept on this phone, then syncs everything again from each connected host. Pairings stay, and how far each conversation was read comes back from the bridges.

### Conversation

The conversation's name in the bar (the agent's name while it has none), the agent and its address under it, or, while the agent's runtime reports it at work, the wave and what it is doing ([agent activity](#agent-activity-and-tasks)), its avatar pulsing; tapping them renames it, except `working on a task`, which opens the task's [sheet](#a-tasks-sheet) when the phone keeps it. Messages bottom-up, anchored at the newest: the screen follows what arrives unless the person scrolled up to read, and stays anchored when the keyboard opens. The messages run under the name bar above them and the composer below them; the name bar takes the status bar's room at the top edge, and the composer's bar reaches the screen's bottom edge, its material filling the navigation bar's room while its field and send button sit above the navigation bar (and above the keyboard when it is open). A day separator in lowercase (`today`, `yesterday`, `mon 3 nov`) starts each day. Each message has its time (`HH:mm`).

- The person's messages: right, on `button-bg`, shown exactly as typed.
- The agent's: left, on `surface` with a hairline, [markdown](#5-messages) drawn, selectable to copy. One the agent sent on its own (`kind: notify`, such as a cron job's) has an "on its own" header; the protocol does not say which job.
- **The agent at work**: three squares rising in turn, a 900 ms wave, from the moment the person's message is sent until the agent answers, and whenever the runtime says it is typing. It stops when the connection ends, when the bridge refuses the message (an `error` naming it, such as `agent_unavailable`), and after 10 minutes with no word from the agent.
- **What it does** (runtimes with the `tools` capability): above the working wave, "Working · n steps" and each tool the agent runs, one a line: its mark (a square pulsing in `accent` while it runs, a check once done, a cross if it failed or a policy refused it), its name in mono, what it does (`ls -la`, `weather Lyon`) and how long it took. When the answer arrives, its steps fold into one line above it ("3 steps", with a chevron), which opens them. When the turn ends with no answer (the runtime stops typing), a step still running is marked done and the steps are no longer shown; an answer that follows still takes them, and the person's next message starts a turn with none. A tool's name and what it does show a hidden character as `⟨U+XXXX⟩` (the app's `Visible` rule). Steps come live from the bridge, which does not keep them: the phone keeps them with the answer they led to, so they stay after the app restarts, on that phone only (another device, or this one after missing them, shows the answer without its steps).
- **What the agent used** (runtimes that report usage, through a bridge with `usage`; enclos `docs/protocol.md`, Usage): under the working wave, `So far:` and the turn's usage as its model calls arrive; once the answer comes, the same line under it (`3 calls · 33.8k in (94% cached) · 96 out`), with the usage glyph, faint. *In* is all the model was sent, cache included, since that is what grows with the context; the share read from the cache shows when the runtime counts it. A turn's usage stays with its answer while the app runs (it is not stored on the phone yet, so a restart drops it). As with steps, a turn that ended with no answer keeps its usage for an answer that follows; the person's next message, from this phone or another, starts a turn from none. A background call that comes once the agent answered (its title, say) adds to that answer, not to the next turn. **Usage** in the conversation's actions opens a dialog with the conversation's whole usage as its bridge summed it (calls, input, cache read, cache write, output, reasoning and total, `not counted` for a count the runtime does not keep), or says why there is none: not connected (it comes with the next sync), a host that does not report usage, or none reported yet. The bridge sends that total with the conversation at each sync, so it holds across restarts and devices.
- **Tasks asked for here**: a live card each, among the messages ([Agent activity and tasks](#agent-activity-and-tasks)).
- Under the messages, why the host is not connected, or what the bridge said, when there is something to say.
- **Sending needs the host connected.** While it is not, the field still takes text, the send button stays off, and a line above the field says so (`Not connected to mac: send once it's back.`); nothing is queued to go later. What was written stays, for each conversation, while the app runs (leaving and coming back keeps it); Forget this host and Clear cache drop it with the conversations. Sending takes it out of the field, but it is sent only once the bridge shows it back as stored: should the connection end, or the bridge refuse it (`error` naming it), first, the text comes back to the field, before anything written since, and the line above says `Not sent:` and why. If the bridge had it after all, the next sync shows it and takes it out of the field again, unless the person changed it. A conversation started on the phone stays a draft until the bridge sends it back, so its start goes again with the next try.
- **The field's keyboard**: the field tells the phone it is a message field, not a generic text box, and that it capitalizes sentences, so a message opens with shift on and each new sentence starts with a capital. The keyboard's ↵ adds a new line, and the arrow beside the field sends. It still takes five lines, and the app still sends exactly the words typed. The box where an answer to an agent's question is written — `Answer`, `Other answer`, `Your answer` — declares the same; every other field (search, a conversation's name, a group's name, a sandbox's name, model ids, paths, cron expressions, the pairing link) keeps the generic keyboard and starts lowercase.
- **The agent's commands** (runtimes with the `commands` capability; enclos `docs/protocol.md`, An agent's commands): typing `/` opens, over the field, the commands the agent's runtime lists, in its order, on `surface`; each `/name` in mono, what follows it faint (`[name]`, `<prompt>`), and what it does on one line. Typing more keeps the commands whose name starts with it, then those that have it elsewhere, whatever the case, with the typed part in `accent`; about four and a half rows show, the rest scroll. Picking one puts `/name ` in the field, the cursor after it, and the list closes, as it does once a space follows the name. A command is sent like any message, and the runtime answers it; the app runs nothing. The bridge sends the list after the agents' and when the runtime lists it anew; it is kept while the host is connected, and dropped by Forget this host and Clear cache. Each name shows once.

Opening a conversation marks it read, as does a message arriving while it is open: unread counts are the agent's messages after the last one read. The bridge keeps how far each conversation was read and sends it with the conversation, at each sync and when it moves (enclos `docs/protocol.md`, How far a conversation was read): a message read on one device is not unread on another, nor after pairing again. The runtime cannot tell, as it does not see what the person reads. A conversation read further while offline tells the bridge at the next sync. A position past the conversation's newest message is taken once its messages came, and never past the newest of them, as the bridge itself never goes further.

## 5. Messages

**Bubble width.** Messages grow with their content up to 90% of the available conversation width, capped at 640 dp/pt on large screens. The conversation keeps its side padding, and every bubble leaves a visible gap on its opposite side. Short messages keep their natural width. Android is built; iOS follows the same limit when implemented.

An agent's message is markdown ([ADR 0002](adr/0002-messages-are-markdown-drawn-by-the-app.md)): CommonMark, with GitHub's tables, strikethrough and bare links. The app draws it itself:

| Markdown | Drawn as |
| --- | --- |
| `**bold**`, `*italic*`, `~~struck~~` | semibold, italic, a line through |
| `` `code` `` | mono, in `accent` |
| `# Heading` (1 to 6) | semibold, 19, 17, then 15 sp/pt |
| lists, ordered or not, nested | a mono marker in `text-faint`, then the item; lists and quotes are drawn 8 deep inside one another, and a deeper one as its words in one plain paragraph |
| `> quote` | a 2 dp `accent` bar, the text in `text-muted` |
| fenced or indented code | mono on `panel-deep`, scrolling sideways |
| table | columns as wide as their widest cell (up to 240), header bold, hairlines between rows, scrolling sideways; at most 12 columns and 50 rows, the header included, with a line above saying how much is shown when there are more |
| `---` | a hairline |
| a single newline | a line break (CommonMark would join the lines; chat is written line by line) |

Nothing in a message is fetched or run:

- an image (`![alt](url)`) shows as its alt text and `↗`, a link to it; the app never loads it;
- HTML shows as its literal text;
- tapping an `http` or `https` link opens the preferred browser's Custom Tab on Android when the link's text is the very address it sends (a bare link); a link whose text is a label, an image's alt text, or an address the network spells otherwise (a look-alike name in another script) first shows the same sheet as an artefact's link (below), for the same reason: its address can carry what the agent wrote, past the label, and leaves the phone outside the sandbox's network policy. `mailto` uses the system mail handler. Any other scheme, and an `http` or `https` link with no host or with user-info (`https://bank.example@evil.example` reads as the bank), is plain text. The browser handles the opened website with its normal state and capabilities. A system URL handler for links that may be opened from the web (`BROWSABLE`) is the fallback when Custom Tabs are unavailable; no handler or a refused launch produces a native notice. Nothing is prewarmed or prefetched.
- a link's text drops hidden characters (bidirectional overrides, zero-width characters: the app's `Visible` rule), so it cannot read as another address;
- a `mailto` link opens the mail app with the recipient, subject and body the agent wrote; the person still decides to send it.

The person's own messages are not markdown: they show as typed. Previews (inbox, and later notifications) are the words without the marks.

### Suggested replies

An ordinary agent message may offer up to four literal reply buttons below its bubble. Each is a nonblank, distinct single line of at most 256 UTF-8 bytes, with the same hidden-character and visible-distinctness rules as questions. Invalid optional metadata leaves the message readable without buttons. Labels wrap in full, including at large text sizes. A tap sends exactly that label as an ordinary person message in this conversation; it uses the normal send receipt and changes no access. Buttons are disabled offline or while that conversation awaits a send receipt, and disappear after any later person message, including one from another device. Reply metadata is saved with history and survives reconnect and cache upgrades. Older apps ignore it. Notification reply actions are not implemented.

Consecutive runtime status lines without attachments fold into one line with their count and an expand control. Ordinary agent messages and attached files are not folded with them.

### Questions

A structured question appears inside its agent's message, using the app's existing choice, field and button styles. The person selects one option, or several when the question allows it, and explicitly taps **Send answer**. Nothing is selected initially, including an option labelled Recommended. Labels wrap in full. **Other** opens a text field and replaces any listed selection; a question without choices offers the text field directly. **Skip question** is a separate explicit action. Empty answers cannot be submitted. The card opens with the app's own line, "The agent asks · answering changes no access", above the agent's text, so a question cannot pass for a sandbox access request. Android is built; iOS follows the same behaviour with native controls when implemented.

The card applies enclos-protocol's question rules before showing or sending anything: at most 12 one-line labels, distinct once joiners are set aside, the encoded size limits, and no hidden character (a control character, a bidirectional mark, embedding, override or isolate, a zero-width or other default-ignorable character, a line or paragraph separator, a tag, a variation selector, a blank filler or a soft hyphen; newlines aside in the question and in a typed answer), so one label cannot read as another. The joiners U+200C and U+200D and the emoji variation selectors U+FE0E and U+FE0F are ordinary text between two non-ASCII characters (Persian spelling, a joined emoji) and hidden anywhere else. A question that breaks them stays readable text. A typed answer is sent with its line breaks as plain newlines; one with a tab or another hidden character is not sent, and the card says why. These rules are written twice, in enclos-protocol (Rust, which the bridge applies) and in the app (Kotlin, `Questions.kt` and `Visible.kt`), with the same test cases: `core-ffi` pins an enclos-protocol commit that has the `question` and `visible` modules, but `core-ffi` wraps only its `noise`, `pairing` and `preview` modules, so the app cannot call those rules yet. Once `core-ffi` exports them, the app should call the crate's rules through the core instead, which iOS then shares too.

How long a question stays open is the runtime's to decide: enclos sets Hermes's `agent.clarify_timeout` to an hour for the app's agents, after which the card shows Expired. An agent that stays disconnected for two hours has its questions expired by the bridge.

Only a message linked to valid structured metadata becomes a question card. An ordinary list, or a linked message whose metadata is unavailable, keeps its readable text. The optional runtime-neutral contract and its ownership/lifecycle decision are in enclos's [Questions protocol](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#questions) and [ADR 0052](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0052-questions-keep-their-runtime-waiter-and-structured-app-controls.md), proposed. Hermes first implements it through `clarify`; the channel hint and registered `enclos:app-questions` skill teach the agent to put options in the tool's choices.

Submitting resolves that exact waiting question; it sends no chat message and starts no new turn. Answer controls are disabled while offline or awaiting a receipt, and are removed after the native question is answered, skipped, expired or cancelled. Read-only expired requests and reminder dismissal are described under Inbox. The card shows the confirmed answer or terminal notice. Another device's answer updates it too. The bridge marks a settlement `confirmed` only when it is the answer a paired device submitted, matched by its request; an answer or a skip the agent's channel reports on its own (a reply typed in the composer, say) reads "Answered, as the agent reports" or "Skipped, as the agent reports". A question may be answered with no answer the contract can carry (the runtime took a reply with a hidden character, for one): the card then says it was answered and shows no choice or text. An unrelated metadata broadcast is not confirmation of this device's submission. A disconnect, a lost receipt, or the bridge's `unconfirmed` error (or an error code the app does not know) may leave the outcome uncertain: the card explains it and does not resend automatically. Its pending state is refreshed by the next sync: the one after a reconnect, or one the card's **Check again** asks for over the open connection. The sync sends every pending question again, so one it sends may be answered again; until it ends the card says it is checking. A refusal the bridge makes before writing the answer to the agent (`agent_unavailable`, `bad_message`, `conflict`, `not_found`, `unsupported`, `not_allowed`) is certain: the card shows why and may be answered again. A runtime restart cannot recreate its old waiting call.

Question definitions, states, revisions and message links are cached per host with conversation history. Older cache versions migrate without losing messages. The newest confirmed revision wins over delayed network events or background cache loads; clearing cache or forgetting a host clears its questions too, and a cached question whose conversation is no longer kept, or which no longer reads as valid, is dropped when the cache loads. An older bridge/runtime keeps native text fallback, and older apps can answer the readable question through the runtime's text interceptor (an option's number or text, or "skip"; another message cancels the question and reaches the agent as a message).

### Runtime approvals

A supporting runtime's approval appears inside its agent's bubble under the app's own heading, "The runtime asks to run a command", then the runtime's text as plain body, the complete native display command and its reason ([ADR 0009](adr/0009-runtime-approvals-use-native-buttons-with-explicit-consent-scopes.md), proposed). The command is selectable text in mono, wrapped so that none of it is out of sight, with every hidden character (a control other than a newline, a bidirectional mark, a zero-width or other default-ignorable character, a soft hyphen; the shared rule of enclos-protocol's `visible` module) written out as `⟨U+XXXX⟩` and a tab as `⟨tab⟩`: what is shown is what runs. A run of two or more blank lines is written as one line `⟨N blank lines⟩` and a run of eight or more spaces as `⟨N spaces⟩`, so a stretch of nothing cannot push part of the command out of sight. A command holding a character outside ASCII carries a notice that some such characters look like others. The runtime's text and the reason are shown the same way.

The conversation opens on its newest item, so a card taller than the screen shows its buttons first. A command of more than four lines, or more than 240 characters, says next to the buttons how many lines and characters it has and that it starts above. Until the start of the command has been on screen, only Deny is available, and the card says so. Neither is rendered as markdown or run by the app. Buttons use the app's existing styles and tokens. An ordinary message containing `/approve` remains a message; native controls require linked, matching typed approval metadata. Approval metadata never uses the ordinary question picker.

Show only the runtime's offered actions, in order: **Allow once**, **Allow for session**, **Always allow**, **Deny**. A direct tap explicitly submits that action; nothing is selected or submitted by default. A Deny-only request offers no allow button. A runtime smart denial can offer only a one-operation override and Deny, or Deny alone. Once is explained in the app's words as this command request alone. A legacy request names the runtime's patterns that Session and Always cover, every command matching one of them, for the native session or persisted in the native profile. An explicitly negotiated native-scopes request instead shows its native explanation of the persistence target under the app's line "The runtime describes these grants as follows:", with any hidden character written out as `⟨U+XXXX⟩` so the runtime's words cannot read as something else. It can offer Once/Always/Deny without inventing Session.

The patterns rule: without `scopes`, a request offering Session or Always must name at least one pattern (at most 16, distinct, with no hidden character), or the card is not shown and the readable text stands; with `scopes`, the description stands in for the patterns, which may be sent, are then checked the same way, and are not required. Allow for session and Always allow each ask for confirmation before anything is sent: a legacy request's dialog names its patterns, a scoped request's repeats the runtime's description and never depends on patterns. Where a scoped card cannot be answered (offline, before sync, an unconfirmed outcome), it shows the runtime's own instructions for answering in the runtime (`scopes.fallback`), written out the same way and marked as the runtime's; not while this device's decision awaits its receipt. Display the full command and reason without shortening them to fit. Other, custom text and Skip are information-question controls and are unavailable here.

Android advertises `runtime_approval_scopes` in each authenticated connection and preserves the supplied scope explanation/instructions with immutable question/cache metadata. The bridge sends extended structured controls only to devices that opt in; older apps receive complete readable native fallback, and older bridges ignore the additive auth field. iOS must negotiate and render the same native semantics when implemented. Host negotiation follows enclos's proposed ADR 0056 ([M5 tracking issue](https://github.com/victorbonnet/enclos/issues/218)). Downgrading over retained independent-scope cache/history requires compatible readers; no cache deletion or host database restore is automatic.

Submission targets the exact pending native request, without sending `/approve` chat text or starting a new turn. For these structured controls, the bridge requires the host's own person, who must also own this conversation, on a still-paired device, and sends approval metadata to no one else: anyone else sees the readable message, which names the offered actions and says only the host's person can answer. The bridge signs each decision it passes on with a key of its own that no sandbox reads, and the agent's channel acts on no unsigned, altered, replayed or stale decision, so a program in the sandbox cannot approve its own command by speaking for the bridge. Runtime approvals are decided with a paired device's buttons alone: typed approval commands (`/approve`, `/deny`, `/yolo`, `/approvals`) are refused by the bridge from everyone, the host's person included, and neither stored nor relayed, and the channel answers any that reaches it itself. This is runtime consent, separate from the sandbox policy inbox: enclos's policy remains in force, and the runtime owns grant persistence and execution. The [runtime approval protocol](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#runtime-approvals), [enclos ADR 0053](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0053-runtime-approvals-use-exact-native-requests-and-explicit-scopes.md) and [enclos ADR 0060](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0060-the-bridge-signs-runtime-approval-decisions.md), both proposed, define that authority, the signed decision and the exact-request contract.

Controls are disabled while offline, awaiting a receipt, uncertain or terminal. Show the confirmed **Allowed once / Allowed for session / Allowed always / Denied** action, or **Expired / Cancelled**. A native decision made elsewhere may report only **Resolved in the runtime**: explain that its decision detail was not received, rather than inventing allowance, denial or scope. Acceptance confirms consent only, not that execution started or succeeded. Canonical broadcasts update the card but do not acknowledge this device's request. Lost replies and ambiguous errors require fresh reconnect sync before another explicit decision; no action, including Deny, queues or resends automatically. A closed card never reopens or addresses the next native request.

Approval metadata, state and message links use the existing host-scoped question cache, retaining immutable definitions and newest confirmed revisions across background loads, history sync and app restarts. Clear cache and Forget this host remove the local copies. Old question records remain compatible. An older app displays the readable message, which decides nothing. This needs updated app, bridge, channel and supporting Hermes APIs.

There is no typed fallback. An approval no card can show (one the bridge refuses, one outside the protocol's bounds, or a bridge or runtime without the capability) arrives as text that shows the whole command and says the app cannot decide it; the channel denies it at once where the runtime resolves its exact request, and the runtime's timeout denies it otherwise. In a bridge-managed group, the buttons target the requesting member directly.

This behaviour is specified once for Android and iOS. Android uses Compose buttons, selectable wrapped command text and a Compose confirmation dialog for Allow for session and Always allow; iOS must use native SwiftUI controls with the same offered scopes, consent rules, exact receipts, terminal states, host-scoped cache and readable text for an approval no card shows. Android is built; iOS is not built yet.

### Held tasks

A held task is background work an agent's runtime started that has stopped and waits for a person before it runs again, such as a blocked task on Hermes's kanban board. The runtime keeps the task; the bridge keeps a card for it in the Home of the agent that started it and sends it to the host's person alone ([enclos ADR 0066](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0066-held-tasks-stay-with-the-runtime.md), proposed; the [held tasks protocol](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#held-tasks)). The app adds no board of its own: a card shows where its Home's history introduced it, or below that history when nothing there introduces it.

**Where it shows.** When a task is held, the bridge adds a `notify` message to the agent's Home, linked to the task (`held_task`); when it leaves `held`, a quiet `status` message linked the same way. Both keep their readable text, which an older app shows as it is. The newest introducing message of a task becomes its card, drawn in the current state of the newest card the bridge sent; an earlier introduction of the same task (one held again) stays text, and the leaving lines stay status lines. A card shows only in its agent's Home, never in another conversation or a group. A linked message whose card the app does not have keeps its text.

A held card that no message of the Home on the phone introduces is drawn below the Home's history, oldest first, after its newest message: so is a task held before the phone kept messages' links (an older app stored its introduction without one, and a sync sends the card again, never that message), or one whose introduction is not loaded yet. It stays there while it is held, and while the outcome of a resume tapped there is still shown. A card that comes before the phone knows its Home (a sync sends the conversations first, so only one that arrives out of that order) is kept, and shows once the Home does.

The optional `resumable` field is a strict JSON boolean: absent means true for older bridges and caches; null, strings, numbers and containers are refused. False remains held and visible in linked history, below history, before Home arrives, and through cache/sync. JSON caching and copies retain false. Capability-only changes use higher bridge revisions; current wins equal revisions. The selected receive path is raw FFI decrypt bytes → `Bridge.kt` → `inbound` JSON → `HeldTask.from`, so the pinned core's older typed card does not strip this field.

**What it says.** The card opens with the app's own line, "Held task · the runtime keeps it; resuming changes no access", then the runtime's words as plain text, never markdown: the title, why it is held, the last error (in mono, folded to four lines with **Show the whole error** when longer than four lines or 280 characters), who it is assigned to when another agent does the work, how long it has been held ("Held since 3 hours ago"), what resuming does for this runtime ("Resume: Runs it again with a fresh retry budget.", left out when the runtime says nothing) and its state: **Held · waiting for you**, **Answered: …** (the person answered it, from the app or, as the agent says, in the conversation; it still waits, on the agent, and says what was answered, or "Answered · waiting on the agent" when the bridge sent no answer), **Resumed from this phone** (only while the phone holds the runtime's confirmation of its own resume, which it keeps in memory) or else **Resumed from the app**, as a lost answer or a restart leaves the card unable to tell which device it was, **No longer held** (it runs again, finished or went away), or **No longer tracked** (the agent's channel stopped reporting held tasks). A state the app does not know is named and offers no Resume. The app reads each text as the bridge cuts it, again rather than trusting it: hidden characters dropped (enclos-protocol's `visible` rule, newlines kept in the reason and the error), the title, assignee and resume line on one line, each cut to the protocol's bound (200, 64, 1,000, 2,000 and 200 characters); a blank title reads as the task's id and a blank reason as "Waiting for a person." A card with a field missing or of the wrong type, an agent that is not `sandbox/agent`, an id that is not one, a task id with a hidden character, or a negative revision is not shown.

A false card opens with "Held task" and shows the runtime's instruction plainly, without a Resume prefix or action; when blank it says "This task cannot be resumed from the app." Its metadata, error and real state remain. The local error disclosure wraps and has a minimum 48dp touch target.

**Who it waits for.** A held task's index row may say whether it waits on the team or on the person (`waits_on`). One that waits on the team is not shown under Needs you and does not count there, while its card stays in its conversation and is answered and resumed as today. A host that does not say leaves the list as it is today.

**Answer from Needs you** ([enclos ADR 0073](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0073-the-person-answers-a-held-task-from-its-card.md), proposed; the protocol's [Answer](https://github.com/victorbonnet/enclos/blob/main/docs/protocol.md#held-tasks)). A card may carry what the agent that started the task wrote for the person when it handed the hold to them (`ask`): the decision, one question; what is blocked; up to four choices, each saying what happens; and which one the agent recommends. The app reads it as the bridge cut it, again (the decision and each choice on one line, cut to 120 and 80 characters, what is blocked cut to 400 with its line breaks kept); a field of the wrong type refuses the card, and an ask the bridge would not send (a blank decision, more than four choices, a blank choice) reads as none. It never drops or reorders a choice: a choice is answered by its index, the bridge's.

When the host's bridge lists `held_task.answer` in `authenticated` (it does so for the host's person only), a held task's request sheet is, in order, laid out so the person can decide from what it shows, without opening Details, and answer with one tap:

| Part | What it shows |
| --- | --- |
| Header | "Needs you", then the agent, and "· Director's task" when another agent does the work (`assignee`) |
| Decision | the agent's decision as the heading; on a card no agent wrote, the task's title |
| Blocked | what the agent says is blocked; on a card no agent wrote (or one whose ask says nothing is blocked), the runtime's reason; in full either way, never cut |
| Choices | one button per choice, each one tap, its label wrapping: the recommended one first, filled like the primary button and marked "Recommended", the others outlined; on a card no agent wrote, **Ask the agent for choices**, with "The agent looks into it and writes its question here, with choices to tap.", then **Resume task** when the runtime allows it |
| Typed answer | folded behind **Answer in your own words** (a full-width text button with a 48dp target that wraps), which opens a field, "Your answer", with **Send**, enabled once the text is one the bridge takes (nonblank, at most 2,000 characters, no hidden character but a line break; sent trimmed); open at once when the ask has no choices, or text is kept (below) |
| State | why the controls are disabled (connecting, the sync, an answer waiting), and what the last answer's outcome was |
| Details | folded: the task's id and title, the runtime's reason unless it is shown above (it is on a held card no agent wrote, or whose ask says nothing is blocked), **Resume task** on a card the agent wrote when the runtime allows it, **View task**, **Open task board** (a task the runtime holds for a board decision), **View conversation** and **Dismiss reminder** |

A tap on a choice, **Ask the agent for choices** or **Send** sends one `held_task.answer` with the card's agent, task and bridge revision and the answer (`{kind:"choice",index}`, `{kind:"agent"}` or `{kind:"text",text}`), under a fresh request id, from the card as it was drawn: a card that changed since is not answered. There is no confirmation: the answer becomes the person's message to the agent, which acts on it with its own tools and gains nothing the same message typed in the conversation would not. While it waits the controls are disabled ("Sending your answer…"). `held_task.result` brings the `answered` card: the sheet says "Answered: …" and the row leaves Needs you at once (the app drops the row of a card it holds `answered` at that row's revision or a newer one, before the host's next index; a newer hold brings it back). An `error` for it:

| Code | The sheet says | The controls |
| --- | --- | --- |
| `not_allowed` | only the host's person can answer held tasks | available again |
| `not_found` | not known on the host | none, until the bridge sends a newer card |
| `bad_message` | the host did not take this answer, so nothing was sent | available again |
| `unknown_type`, `unsupported` | this host's bridge cannot take answers; update enclos there | available again |
| `conflict` | the task changed since the card was shown; refreshing | after the sync |
| `internal`, any other code, no reply within 35 seconds, a reply it cannot read, a connection that ended first | the answer may have reached the agent; refreshing | after the sync |

A card the host sends that this app cannot read (a newer bridge's form, or a bug) is never shown in place of the kept one; when it is newer than the kept card, the kept card offers no answer or Resume, since either would only meet `conflict`, and says "<host> sent a newer version of this task that this app cannot read. Update the app to answer." until a readable card of that revision or a newer one comes. A newer card also takes away what the last attempt said (a refusal, or "Checked: …"), unless an answer still waits or is in doubt. An answer is never queued while offline or sent again on its own. A sync sends every card still held or answered (only held ones are in Needs you), so after a doubted answer the card reads "Answered: …" if the bridge took it, and otherwise is still held and says the host still lists it as waiting for you. The sheet of a task whose answer from this phone waits, is in doubt or was taken stays open after its row leaves Needs you (the bridge sends the answered card and its index before `held_task.result`), to say what was answered. Whether a host takes answers is what its last `authenticated` said: the app keeps it when the connection ends, so the sheet keeps the answer layout and its typed text, with its controls disabled and the reason ("Connect to … to answer."), until the next connection says otherwise; after an app restart the layout before answers shows until the host connects. The bridge's own answers, "Answered in the conversation." (an ask the agent settled) and "Asked the agent to look into it.", read as they are, without "Answered:". A bridge without `held_task.answer` gets the sheet as before (below) and no answer control; the agent's notice in the Home still reads on its own, and the person answers in the conversation. The conversation card of an `answered` task shows "Answered: …" as its state line, and an answered card never shows under Needs you.

**The unsent answer.** Text typed in **Your answer** is kept in the app's memory, for the app's current session only: it survives closing and reopening the sheet (View conversation, then back to Inbox), a configuration change and a lost connection, and is lost if Android closes the app. It is never written to saved state, the cache, preferences or a backup, never logged, put in a notification or copied to the clipboard by the app, never recovered after a restart and never sent on its own. While it is in the field the sheet says, under it, "Not sent. Kept temporarily in this app." and "It may be lost if Android closes the app."; after a send was tried with that text, "Kept temporarily in this app." instead, as the outcome notes say whether it may have reached the agent. It is kept for the exact card it was typed for (host, agent, task, revision and every field of the card; another host with the same name, or another task, never gets it) and the host's connection then: a newer card of the task, or a new connection (`authenticated`), takes it out of the field, as earlier text. The sheet then says "This request changed. Your earlier text has not been added to it." or "The connection changed. Review this request before reusing your earlier text.", shows the current, empty **Your answer**, then "Earlier text · read-only" with the text (selectable, not editable), "Review the current decision, blocker and choices first. Using earlier text fills Your answer; it does not send it.", **Use text in Your answer** (enabled only when the request can be answered now and the field is empty) and **Discard earlier text**; both texts are kept until the person uses or discards the earlier one. Waiting, a send that failed, any refusal, a doubt, a connection that ended, or an answered card before its result (and a held card after it) keep the text; only `held_task.result` bringing the `answered` card for this phone's typed answer drops it, and only if the text was not edited since it was sent. Emptying the field drops it; so do **Discard earlier text**, removing the conversation, forgetting the host, pairing it again and clearing the cache. Dropping it is not a secure erasure of the app's memory.

**Task board from Needs you.** On a bridge without `held_task.answer`, the sheet shows the title, the runtime's reason, Resume and **View task**, then **View conversation** and **Dismiss reminder**. When a held task offers Resume, its request sheet explains why the action is disabled. For a held task the runtime holds for a board decision, the sheet shows the runtime's instruction or the fallback above, and **Open task board** (under Details in the answer layout). **Open task board** asks a connected bridge that advertises `held_task.board` for the board of the card's agent, task and revision. The app opens the reply in the browser only for the matching request from that paired host, on the HTTPS origin from pairing. The short-lived handoff is used once and stays out of the app's saved state. Leaving the sheet or the app cancels the pending open. If the host is offline or the open fails, the sheet explains what happened. A busy host asks the person to try again shortly.

A previously saved board address opens directly when the bridge is disconnected or lacks `held_task.board`. A capable bridge still gets the primary action, with the saved address available as a separate browser link because board availability can also depend on the runtime. The sheet lets the person edit or remove that saved address. A connected older bridge with no saved address shows the host update message. The host's confirmation that an agent was removed or forgotten clears its saved address. Forgetting or replacing the pairing removes that host's saved addresses. Android implements the board link.

**Resume.** It is the one action, and only while the card is held and resumable. It is enabled when the host is connected, its sync since the connection opened has ended, and no resume of this card is waiting for its answer; otherwise the card says why. A tap sends `held_task.resume` with the card's agent, task and bridge revision, under a fresh request id, and nothing else; there is no confirmation, as resuming widens no access: the work runs again under the sandbox's existing policy. A card that changed since it was drawn is not resumed. The answer is matched by that id: `held_task.result` shows the card resumed from this phone. An `error` for it shows on the card:

| Code | The card says | Resume |
| --- | --- | --- |
| `agent_unavailable` | the agent is not connected, nothing was sent | available again |
| `not_allowed` | only the host's person can resume held tasks | available again |
| `not_found` | not known on the host: the host (or its runtime) has no such held task | none, until the bridge sends a newer card |
| `bad_message`, `unknown_type` | this host's bridge cannot resume held tasks; update enclos there | available again |
| `unsupported` | This request could not resume the task. Refresh without resend; this proves no permanent capability from prose | after fresh sync, only if still resumable |
| `conflict` | the task changed since the card was shown; refreshing | after the sync |
| `unconfirmed`, `internal`, any other code | the task may have resumed; refreshing | after the sync |

A resume is never queued while offline or sent again on its own. When its outcome is not known (`unconfirmed`, `conflict`, `internal`, a code the app does not know, an answer it cannot read, no answer within 35 seconds, past the bridge's own 25, or a connection that ended first), the card says the task may have resumed, the app asks the host for a `sync` over the open connection (else at the next one), and Resume waits until that sync ends; the bridge sends at every sync each card still held. Only a new tap resumes it again. A late answer to a request whose wait ran out still updates the card on the same connection. `not_found` comes from the bridge (no such card) or from the runtime, through the plugin, after it was asked: the card then says the host does not know the task, in place of its state line, and offers no Resume; this is the phone's own note, not kept, and a card from the bridge at a higher revision replaces it. Whether a card goes back to `held` after a confirmed resume is the bridge's to decide, from the runtime's reports; the app shows whichever card has the highest revision.

**Kept.** Cards are cached per host with the conversation history, by host, agent and task, with each message's link: they survive an app restart and show at once, offering Resume or an answer only after the next sync. The bridge's revision decides: the app keeps the highest it saw for a card and ignores a lower or equal one, whether it comes live, from a sync or from the cache. A cached card which no longer reads as valid is dropped when the cache loads, and so is one whose Home is no longer kept; while the app runs, a card of a Home not known yet is kept (above), and the next sync sends it again if it is still held. Clear cache and Forget this host remove them; a conversation the bridge deletes takes its cards with it. Older cache versions migrate without losing messages; a message stored before the update has no link, and its task's card shows below the history as above.

**Held task details.** View task works from a Needs you sheet and a held-task conversation card, including tasks that cannot resume. It uses `held_task.get` with the reporting creator and complete opaque board reference, only when the host and creator advertise support. The bridge checks host-person ownership and the exact known reference; Hermes reads that board and creator's task read-only. The app never strips a board prefix to guess a task-list id. Description, comments and history use the existing task sheet, are fetched on opening and kept only in memory; unavailable/offline details explain why. Related tasks from this board-scoped view are shown without guessing navigation targets. Android implements these views; iOS is not built.


This behaviour is specified once for Android and iOS. Android draws the card in Compose inside the introducing message's bubble, or in a bubble of its own below the history, with the existing primary button and small-text styles; iOS must use native SwiftUI controls with the same states, Resume and answer rules, outcomes and cache. Android is built (the answer layout in `HeldTaskAnswers.kt`); iOS is not built yet. The rules are written in Kotlin (`HeldTasks.kt`, `HeldTaskClient.kt`) rather than called through `core-ffi`, as for questions: the app's pinned `enclos-protocol` predates the ask and the answer, which it reads and writes as JSON, so the pin need not move for them.

### Sending files

In a direct conversation or Home, an attach control beside the composer offers Camera, Photos and Files through the system's own pickers, without storage permissions or kept URI grants; groups have none. It needs the bridge's `message.begin` and the agent's `incoming_files`. `incoming_images` depends on `incoming_files`: without it the agent takes documents only, so Camera and Photos are disabled, saying why, Files still offers documents, and each image chosen in Files is refused by name. Both are checked again when a message goes, an explicit retry included: an agent that no longer takes images has its images named and nothing goes. The attach control is off offline and while a send is under way. Up to four files, each 1–10,000,000 bytes, accompany text or form a message by themselves; the photo picker allows at most the slots left. Each file is a chip with its image's thumbnail or a file mark and its full name, wrapped, which does nothing when tapped, and its own 48 dp Remove button; chips sit side by side when they fit. Preparing and sending show progress.

Camera requests CAMERA permission when needed; before its answer no capture is created or launched. Denial shows “Camera permission was not granted.” and leaves no capture. If no camera can handle the request, it shows “Camera unavailable.” QR scanning is unchanged.

Camera and Photos results are decoded and written again, at most 2,048 px on their longest side, so their source metadata (place, device, time) does not go. What an image is comes from its own first bytes, not its provider's media type: a PNG, or any image with transparency, is written as PNG, keeping its transparency; the rest, HEIC included, as JPEG. Camera and Photos use generic names, photo.jpg or photo.png, numbered before the extension for duplicates, independent of provider names, device and time. A GIF from Photos is refused under the generic photo.jpg label, because its frames cannot be written again without losing its animation; from Files it goes as it is. Files keeps each document's name and exact bytes (a PNG's transparency, a GIF's frames); its type is the protocol's for its extension, whatever the provider calls it (a `.py` reported as `application/octet-stream` goes as `text/plain`). Names follow enclos-protocol's `incoming::check_name` and are refused, never changed; the app's tests run the protocol's canonical name corpus. A name repeated in a selection, or already in the draft (two camera photos), gets a number before the extension. Each refused Files document is named, its hidden characters written out, with a reason in the app's words; the others are kept.

Prepared bytes are held in memory only, by one owner at a time (the draft, then its send), within one budget of 80,000,000 bytes for the whole app, reserved as they are read: a selection that does not fit is refused, and nothing waiting to send is evicted. Each file's bytes are released once, only after any upload worker retaining them has retired: on the send's receipt, its final refusal, a removal, a discard, a cancelled or failed preparation, the conversation's deletion or the host's forgetting. Each conversation, by host, has a newer draft and at most one send: preparing, sending (with progress), awaiting its receipt, refused, or of unknown delivery. Progress and a receipt never show a failure. A refusal the bridge names (`unsupported`, `not_allowed`, `bad_message`, `operation_failed`, correlated by the send's id) is final: its reason shows with the send's words and file names, which are all it keeps, with Dismiss and no Retry; a late receipt does not undo it. A lost connection, no receipt within 60 seconds, or another error code (`internal`, `unconfirmed`, one the app does not know) leaves delivery unknown: the original is kept unchanged, and **Retry original message** sends the same id, text and files again from byte zero (check history first: it may be stored), or the person discards it. Nothing is resent by itself. The receipt timeout settles that send only; the shared connection and other messages stay. A conversation whose send is unsettled stays reachable in Inbox, search and the agent's conversations even before history arrives.

The receipt (`ack`) means the bridge stored the message, not that the agent's model read it. A refusal after the receipt (`error` whose `of` is the send's id) is told once in the send's own conversation, whichever is open, naming its files, and a repeat for that send is ignored, never shown elsewhere; only the names of the 32 latest sends are kept for this, never their bytes. The bridge also adds the refusal to that conversation's history as a `status` message (enclos #298), which the app keeps and shows as any status line, after a reconnect or a restart, with no live correlation; the app reads no delivery state from it. The absence of a refusal is not taken as delivery to the model.

Choosing a picker records, as saved state, which conversation asked, and the camera's file. A new unsent conversation can restore its empty draft owner for the exact still-paired host, unless already entered or deleted; prepared bytes and grants are not restored. A result returning after rotation or the app's recreation goes to that conversation only; one whose conversation cannot be found (its saved state lost, or the conversation gone) is not put in another: the conversation shown says so, to choose or take it again. A camera file is read only from the app's private camera folder. A cancelled capture is deleted, as is one whose conversation is deleted or forgotten, or the cache cleared, while the camera is open; the app's state ending (which may be its recreation) deletes none, and a capture restored after the app's recreation is kept for its result. One abandoned by the app's death, its result never returning, stays in the app's cache until the system or Clear cache removes it.

A suggested reply preserves the existing text draft and sends no draft files. If disconnected before confirmation, its text is restored before the existing draft, separated by a blank line, as for other text messages.

Only the receipt of the send's own id settles it: history has fresh ids, and a message with attachments shown back settles no text send, ordinary or suggested. Leaving an empty, never-started conversation discards its draft; leaving one with an unsettled send keeps it, and navigation never closes the shared connection. Forgetting or replacing a host retires its drafts and sends. Restarting discards drafts and unsettled sends; nothing is queued or resumed. Parts are 45,000 bytes, paced against the connection's queue. Own history uses the existing attachment thumbnails, names and viewers fetched from the bridge.

### Files


An agent's message may carry files: an image it made, a chart, a document (enclos `docs/protocol.md`, Files). The app fetches each from the bridge over the conversation's connection, in parts, when the message is first shown: on an unmetered network (Wi-Fi), any file up to the bridge's 25 MiB; on a metered one (mobile data, a hotspot, as the phone's system counts it), a file above 10 MB only when tapped, so an agent cannot make the phone pull it over mobile data unasked, and by itself once the phone is on an unmetered network again. With no network, or before the system says, the network counts as metered. It keeps each in its cache (never backed up), in a folder per host and file; a file whose id is not of the bridge's form (letters, digits and `-`, as a UUID) is not kept. Tapping an available file opens its viewer in the app, with Back, its name and Share. Sharing starts only from that explicit action. A file that did not come says why and is fetched again when tapped: a fetch the connection broke, a part out of order, or a file the phone could not write (storage full); it goes on from where it was. A cached file cleared by the system is fetched again when tapped. A message with files and no words previews as "Image", or the file's name.

An image in a format the phone decodes (PNG, JPEG, GIF, WebP, HEIC or HEIF, BMP) shows in the bubble, above the words, decoded at the screen's size, in a box of its own shape held between 1:3 and 3:1, the image fitted inside; any other image type (SVG, TIFF, AVIF), or an image that fails to decode, shows as a file line instead, which opens the document viewer with its notice and Share; tapped, it opens full screen, edge to edge, on near black in both themes (as photo viewers do: the image is the only colour), with Back, its name and Share over it on a shade, which a tap on the image hides or shows. Pinch zooms it, up to 6×, around the fingers; while zoomed it moves with a finger, its edges held at the screen's; a double-tap zooms 2.5× on that point, or back to the whole image. It is decoded at up to 4,096 px on its longest side, to stay sharp when zoomed; an image is never decoded above 64 MB in memory, a smaller sample being taken (Android draws no bitmap above 100 MB), and one that would still be larger shows as a file line.

Other files show as a line with their name and size. HTML opens as an artefact as described below. A PDF (`application/pdf`) opens in a native, read-only document viewer with scrolling and zoom ([ADR 0008](adr/0008-pdfs-open-in-a-native-viewer-with-isolated-rendering.md), proposed); external PDF links and form filling are disabled. Other text (`text/*`, excluding HTML, plus `application/json` and `application/xml`) shows literally as selectable UTF-8 text, without running content or fetching resources, up to 1 MiB; it is drawn in blocks of at most 4,096 characters as it scrolls into view, so a large file is never laid out at once (a block ends after a line break when one fits; a block that goes on with a line too long for one starts with a faint arrow, outside the selection, so the cut does not read as a line break). Media types choose the viewer; a filename extension alone does not. An unsupported format, invalid or oversized text, password-protected PDF or failed PDF preview shows a notice inside the viewer, with Share, and **Open in another app** when the file may be opened elsewhere (below), still available. No failure automatically hands the file elsewhere. Android is built; iOS follows the same behaviour with its own native viewer when implemented.

**File names** are the agent's: a file's name, wherever it is shown (its line, a viewer's bar, an image's description, a conversation's preview, the label handed to another app), drops hidden characters (controls, bidirectional overrides and isolates, zero-width and other default-ignorable characters, tag characters and blank fillers; a joiner or emoji variation selector stays only between two non-ASCII characters: the same rule as enclos-protocol's `visible` module), so `invoice`, U+202E, `fdp.apk` cannot read as `invoicekpa.pdf`. The file is kept under a name of letters, digits, `.`, `_`, space and `-` only, without a leading dot and at most 80 characters, a longer name shortened before its extension so the extension stays. Android is built; iOS follows the same rule when implemented.

**Share** hands that one original file to another app through the system's share sheet. The document viewer also offers **Open in another app**, an explicit handoff to a compatible app, only for a file another app may be asked to open ([ADR 0008](adr/0008-pdfs-open-in-a-native-viewer-with-isolated-rendering.md)): its media type is on a fixed list (PDF, plain text, CSV, Markdown, common photo, audio and video formats, and office documents) and its name ends in one of that type's extensions. The agent chooses both, and another app may read the type back from the name's extension, so a type a browser or installer would run (HTML, XHTML, SVG, XML, JSON, an APK) or a mismatched extension (`page.xhtml` as `text/plain`, `invoice.pdf.apk` as `application/pdf`) is never opened elsewhere: such a file offers Share only. Both actions go through the system's chooser, so the person sees which app gets the file. Android uses `ACTION_SEND` for Share and `ACTION_VIEW` for Open in another app, each in `Intent.createChooser`, with a read-only grant for that attachment's cached `FileProvider` URI. A missing cached file, unavailable handler or refused launch produces a notice; if the cache was cleared while the viewer was open, close it and tap the file to fetch it again. The receiving app handles the file outside this viewer's controls. These actions use the existing attachment cache and protocol; no bridge or runtime change is needed.

**Static HTML artefacts.** A self-contained UTF-8 HTML attachment opens as an artefact ([ADR 0005](adr/0005-static-html-artefacts-open-in-a-separate-viewer.md), proposed). An attachment whose media type is `text/html` has a card with its name and size that offers to open the page; a `.html` name alone does not make another media type an artefact. The viewer fills the screen, with a native bar for Back, its name and Share, and a scrollable page below. Loading and a failure to read the page are shown there; Back and Share stay available. A page larger than the attachment limit of 25 MiB or with invalid UTF-8 is refused. Share first asks: the app chosen shows the original HTML file its own way, may run scripts it holds and load what it links to, outside this viewer's controls.

The page may use HTML, inline CSS and data images or fonts. JavaScript, storage, network requests, file and content access, forms, automatic outgoing navigation and native bridges are unavailable; relative resources do not load. A link to an anchor in the same page may scroll there. A tap on a main-frame `http` or `https` link first shows a sheet with the destination's host as the network spells it (punycode, so a look-alike name in another script shows as `xn--…`) and its whole address, non-ASCII percent-encoded, in a box that scrolls; an address longer than 2,048 characters once encoded is not opened, and a notice says so; **Open** hands it to the same browser as a conversation link, **Cancel** stays. The private page stays in its viewer. The sheet is there because a page decides what a tap lands on (a link can cover the whole page) and its address can carry anything the agent wrote into it, which then leaves the phone outside the sandbox's network policy. Subframes, redirects, navigation without a user gesture and other schemes are meant not to reach the sheet (see To verify). The opened website uses the browser's normal network access, cookies and site permissions, outside the private viewer's controls. The private page receives no keys or app state. These controls are written for Android; platform probes remain in [To verify](#to-verify). HTML in message text stays literal, as above. Interactive pages, external assets and multi-file sites are not part of this version. The file uses enclos's existing attachment delivery, cache and ownership checks; there is no separate artefact service or history.

The runtime's plugin tells the agent what the app draws, so that it formats when it helps (Hermes: the plugin's `platform_hint`, in enclos).

An initial static-viewer probe on an Android 17 / API 37 emulator, Google WebView 145.0.7632.218, rendered inline CSS, Unicode text and an embedded data PNG. The script did not execute; a frame reported `ERR_BLOCKED_BY_CSP`; external styles, images, frames and script fetches never reached a local request counter that a separate emulator request proved reachable. Form submission and file/content link taps left the page in place. The browser-link handoff and remaining platform probes are listed below.

## 6. Motion

Short and functional, never decorative: something moves to show where it came from or went. Durations: 150 ms for a change in place, 250 ms for a screen or a message arriving, 150 ms for what leaves. Arriving decelerates, leaving accelerates.

- A full screen arrives over the tabs: it slides in from the right edge, opaque, while the tabs drift a tenth of the width to the left under it. Going back is the same move reversed: the screen slides off to the right, uncovering the tabs drifting back. Both take 250 ms at an even pace, so a finger can drag the move: with the back gesture the screen follows the finger and goes or returns where it is let go.
- The Inbox and Agents views slide side by side with a horizontal swipe; tapping their switch slides to the chosen view in 250 ms.
- A message fades in while the others slide up; an agent that moves to the top of the inbox slides there with its conversations, and those it unfolds fade in.
- Badges, chips, pairing steps, the send button and the theme change smoothly.
- An agent at work: its avatar's corners swell out of it and fade, every 1.4 s; the working wave beside it.
- With the system's animations turned off, transitions end at once, the working wave stands still and an avatar does not pulse.

## 7. Theme

Light or dark: the system's setting by default. Once the person chooses (System · Light · Dark, in Settings, Appearance), the app keeps their choice on this device until they choose System again. Switching crossfades the colours; the screen is not rebuilt. The colours are the design system's tokens, the same in both apps. The bars' material crossfades with the palette: its tint is `glass`, one of the tokens, so a theme switch does not flash the bars.

## 8. On the phone

- **Keys**: the device's signing key is made in, and never leaves, the platform's key store; the Noise key is wrapped by it.
- **Stored**: the paired hosts (each bridge's address and key, the device's id there, the wrapped Noise key), the last message read per conversation, the theme, whether the app lock is on.
- **Conversations are kept on the phone**: each host's agents, the conversations, their names and archived state, every message with its files' descriptions, and the steps of each answer; each host's tasks too, apart from the conversations' copy, as its policy requests are. They show when the app opens, before any connection, and while a host is unreachable; a sync then brings only what is newer. The copy is read off the main thread, in two passes: first what the first screens show (every conversation with its last message, and the last 40 messages of the 10 most recent), with the launch screen kept until then (at most a second) and the connections opened after it; then every other message, merged in. Until that second pass ends, search and unread counts see only the first pass's messages. The bridge stays the source: what the phone keeps is what the bridge sent, and a conversation started on the phone is kept once the bridge confirms it. Pairing again with a host forgets what it sent before. A message that cannot be written (a full disk) leaves no gap: no later message of that host is kept until the app starts again, so the next sync, which starts after the newest message kept, brings it back. A kept row the app can no longer read is skipped, not fatal. A conversation is known by its id: one that a host's bridge sends with the id of another host's conversation is ignored. The copy is in the app's private storage, readable by the app only in a release build, and not encrypted by the app itself: it is as safe at rest as the phone's own storage encryption makes it. Files stay in the cache, which the system may clear: they are fetched again when shown.
- **Nothing leaves the phone** ([ADR 0003](adr/0003-nothing-of-the-app-leaves-the-phone.md)): no backup, no transfer to a new phone. A new phone pairs again.
- **Debug builds only, for now**: the app is built as a debug build only (`assembleDebug`, locally and in CI); no release build is configured, signed or built yet. A debug build is debuggable: on a phone with USB debugging on, `adb shell run-as` reads its private storage (the kept conversations, preferences, cached files and wrapped Noise keys). What this section says about data at rest holds for a release build, not for these: `run-as` needs no backup, so it reads a debug build's storage whatever its backup settings. The backup exclusions above are in the manifest of every build.

### App lock

For a phone lost or left unlocked: with the app lock on, the app asks the person to prove it is them, with a strong biometric the phone has (fingerprint, or a face unlock the phone rates as strong; a weak face unlock, which a photo may fool, does not count) or else the phone's own screen lock (PIN, pattern, password), when it opens and when it comes back after a minute or more in the background. Until then the app shows only a lock screen (the mark, "Enclos is locked", and Unlock): nothing else of the app is drawn, so no screen, dialog, sheet or menu left open is there to see or reach, by touch, keyboard or accessibility services, and no message is marked read. Once unlocked, the app is back on the screen and the place the person left. Back leaves the app. The prompt shows on its own as the app opens and each time it comes back locked; after a cancel, Unlock asks again, and the lock screen says what the system said (cancelled, too many attempts). While the lock is on, the app's window is secure: screenshots, screen recordings and casts show nothing of it, nor do the recent apps.

It is off until the person turns it on in Settings, Security, which needs a screen lock on the phone (else Settings says to set one) and asks to unlock once, so a lock that cannot be opened is never set. Turning it off asks to unlock too, so someone who picks the phone up in the minute after it was put down cannot turn it off. A phone whose screen lock is removed has nothing left to unlock the app with: the lock then turns itself off as the app opens or comes back, rather than lock the person out, and Settings says so. It hides the app; it does not encrypt what the phone keeps, nor tie the keys to it: the conversations and keys are as safe at rest as the phone's own storage encryption and key store make them, and the connections stay open behind the lock, so messages keep arriving.
