# Static HTML artefacts open in a separate viewer

Amends [0002](0002-messages-are-markdown-drawn-by-the-app.md): message text keeps its native markdown rendering and literal HTML, while a separately opened HTML attachment may use a web view. Delivery and ownership remain enclos's existing file contract ([enclos ADR 0048](https://github.com/victorbonnet/enclos/blob/main/docs/adr/0048-artefacts-are-static-html-attachments.md), proposed).

Decision (proposed): a self-contained UTF-8 HTML attachment opens as an **artefact**, in its own full-screen viewer with Back, its name and Share. HTML, inline CSS and embedded data images or fonts are the rendering contract. The viewer disables JavaScript, storage, network loading, filesystem and content access, forms and automatic outgoing navigation, and exposes no native bridge. The page receives none of the app's keys, connection or conversation state. Android uses a WebView with an in-memory document at a synthetic HTTPS address, a restrictive response Content Security Policy and refusal of every other resource request; iOS will need equivalent controls before offering the feature. Same-page anchors stay in the viewer. A tap on a main-frame HTTP(S) link shows the destination's host (punycode) and whole address, and the person's confirmation opens the preferred browser's Custom Tab, falling back to the system URL handler if unavailable; redirects, subframes, navigation without a user gesture and other schemes stay blocked in the private page. Once the person opens a website, the browser handles that website with its normal state and capabilities. A followed link leaves from the phone, outside the sandbox's network policy, carrying whatever the agent wrote into its address; the page decides what a tap lands on, so the gesture alone does not show the person's intent, and the confirmation does. HTTP(S) links in conversation markdown use the same browser surface, after the same confirmation unless the link's text is the very address it sends: a label can hide what the address carries just as a page can; `mailto` keeps the system mail handler.

Reason: a platform web view renders a generated document's layout without building another HTML renderer. Keeping the private page offline and separate from conversation text bounds what an agent's page can do. A person can follow a web link in the browser without publishing the artefact or giving its viewer network access. Interactive pages, external resources and multi-file sites are outside this first version. These are the intended controls; the spec's To verify list tracks the platform probes still needed.

## Considered options

- **Custom Tabs for the private HTML document.** Custom Tabs share the browser's cookies, permissions and other browsing state, as the [Chrome overview](https://developer.chrome.com/docs/android/custom-tabs) explains. The [navigation callback](https://developer.android.com/reference/androidx/browser/customtabs/CustomTabsCallback#onNavigationEvent(int,android.os.Bundle)) reports navigation events; it does not provide the viewer's request veto or WebView settings. Chromium's [security FAQ](https://chromium.googlesource.com/chromium/src/+/main/docs/security/custom-tabs-faq.md) also excludes network request interception from the embedder's access. These APIs therefore do not supply this document's per-view offline controls. Keep the private HTML in its own WebView.
- **Custom Tabs for HTTP(S) links.** A website the person deliberately opens belongs in the browser, with its address bar, site permissions and existing browser state. No browser session is prewarmed and no URL is prefetched. Only the chosen URL is handed over; the private artefact remains in the viewer and no automatic page navigation starts a browser.
